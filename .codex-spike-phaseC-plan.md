# Tvivo Windows Rewrite Spike — Phase C Architecture Plan

Status: planning only. This document does not create the solution, projects, or
code. The proposed spike root is `D:\HCode\Tvivo\windows-spike\`.

Decision tags used throughout:

- **KNOWN** — established by the Phase A/B evidence or an explicit stack constraint.
- **ASSUMED** — a deliberate implementation choice for this vertical slice that is
  reasonable but still needs confirmation during implementation.
- **NEEDS SPIKE** — cannot safely be treated as settled until a focused experiment
  or manual/integration test produces evidence.

## 1. Proposed solution and project structure

The four-production-project shape is retained. It is the smallest split that keeps
provider-neutral domain rules, provider/storage details, native playback, and WinUI
composition from becoming one coupled project. A separate shared abstractions
project is not added: its contracts are small enough to live in Core.

```text
windows-spike/
├── Tvivo.sln
├── src/
│   ├── Tvivo.App/
│   │   └── Tvivo.App.csproj
│   ├── Tvivo.Core/
│   │   └── Tvivo.Core.csproj
│   ├── Tvivo.Infrastructure/
│   │   └── Tvivo.Infrastructure.csproj
│   └── Tvivo.Playback/
│       └── Tvivo.Playback.csproj
└── tests/
    ├── Tvivo.Core.Tests/
    │   └── Tvivo.Core.Tests.csproj
    ├── Tvivo.Infrastructure.Tests/
    │   └── Tvivo.Infrastructure.Tests.csproj
    ├── Tvivo.Playback.Tests/
    │   └── Tvivo.Playback.Tests.csproj
    └── Tvivo.App.Tests/
        └── Tvivo.App.Tests.csproj
```

- **KNOWN:** `Tvivo.App` is the WinUI 3 executable and composition root.
- **KNOWN:** `Tvivo.Core` contains provider-neutral domain models, contracts, and
  playback-neutral value types; it has no WinUI, VLC, SQLite implementation, or
  Xtream DTO references.
- **KNOWN:** `Tvivo.Infrastructure` owns Xtream HTTP/DTOs/mapping, SQLite, and
  DPAPI-backed credentials.
- **KNOWN:** `Tvivo.Playback` owns the two engine adapters and their native/UI host
  integration behind one playback contract.
- **ASSUMED:** Four matching test projects are useful for ownership and fast
  targeted runs. `Tvivo.App.Tests` initially contains view-model/service tests;
  WinUI UI automation is not made a prerequisite for the spike.
- **ASSUMED:** No separate `Tvivo.Contracts` project is needed. If contracts grow
  substantially, extracting them is a later refactor, not part of this slice.

### Project references and dependency direction

```text
Tvivo.App          ──> Tvivo.Core
                   ──> Tvivo.Infrastructure
                   └─> Tvivo.Playback

Tvivo.Infrastructure ──> Tvivo.Core
Tvivo.Playback       ──> Tvivo.Core

Tvivo.Core           ──> no production project
```

Test references are one-way and mirror the production owner:

```text
Tvivo.Core.Tests           ──> Tvivo.Core
Tvivo.Infrastructure.Tests──> Tvivo.Infrastructure, Tvivo.Core
Tvivo.Playback.Tests      ──> Tvivo.Playback, Tvivo.Core
Tvivo.App.Tests           ──> Tvivo.App, Tvivo.Core
```

- **KNOWN:** Core must not reference the other production projects.
- **KNOWN:** Infrastructure may reference Core abstractions, but Core must not
  know that SQLite or Xtream implements them.
- **KNOWN:** Playback may reference WinUI and VLC packages because it is the
  native integration boundary; this does not violate the Core rule.
- **ASSUMED:** App is allowed to compose the concrete Infrastructure and Playback
  registrations. Core-facing code receives interfaces through dependency
  injection.
- **NEEDS SPIKE:** Whether the WinUI test runner can load both native playback
  packages in one test process. Engine behavior tests should remain adapter-level
  and use fakes where a native host is unnecessary.

## 2. Core domain and contracts

### Domain models

These are plain C# records/classes with no serialization, ORM, provider, or UI
attributes.

`ProviderAccount`

- `AccountId: string` — stable identity derived from normalized endpoint host,
  port, and username using SHA-256; suitable for cache/account partitioning.
- `Endpoint: ProviderEndpoint` — scheme, host, and port, represented without
  Xtream path conventions.
- `Username: string` — provider login identity, not a password.
- `DisplayName: string?` — optional user-facing label.
- `MaxConnections: int?` — value reported by the provider when known; not an app
  policy and not required for catalog rows.
- `ExpiresAt: DateTimeOffset?` — optional provider-reported expiry.

`ProviderEndpoint`

- `Scheme: string` — normally `http` or `https`.
- `Host: string` — normalized host/address.
- `Port: int` — explicit port.

`ChannelGroup`

- `ProviderAccountId: string` — ownership boundary.
- `Id: string` — opaque provider group identifier.
- `Name: string` — original group label, never assumed numeric.
- `DisplayName: string` — cleaned but loss-minimizing rendered label.
- `SortOrder: int?` — provider/order hint when available.

`Channel`

- `ProviderAccountId: string`.
- `Id: string` — opaque stream identifier; never parsed as an integer.
- `GroupId: string?` — opaque group identifier.
- `Name: string` — original provider title.
- `DisplayName: string` — normalized title for UI rendering.
- `LogoUri: Uri?` — optional artwork address.
- `AddedAt: DateTimeOffset?` — provider first-added timestamp when usable.
- `SortOrder: int?` — optional provider ordering.
- `Source: StreamSource` — playback source description.
- `Metadata: IReadOnlyDictionary<string, string>` — only bounded, deliberately
  mapped neutral metadata; no raw DTO is carried through Core.

`StreamSource`

- `StreamId: string` — opaque source identifier.
- `Kind: StreamKind` — currently `Live` for this slice, extensible to movie and
  episode without changing the source shape.
- `ContainerExtension: string?` — normalized extension when supplied; the field
  name is deliberately provider-neutral.
- `DirectUri: Uri?` — an already-authorized direct source if a provider supplies
  one; it is not required and must not be preferred blindly.
- `Duration: TimeSpan?` — optional duration; absent for live.
- `AudioHint: string?` and `VideoHint: string?` — optional neutral hints only.

`StreamKind` is an enum with at least `Live`, `Movie`, and `Episode` planned as
neutral values. The Live-only slice only produces `Live`.

- **KNOWN:** Xtream live uses `ext`, while VOD/episode responses commonly use
  `container_extension`; the mapper normalizes both into `ContainerExtension`.
- **KNOWN:** IDs are opaque strings. Episode IDs in particular must not be modeled
  as integers; the same discipline is applied to live IDs.
- **KNOWN:** `direct_source` is commonly empty, so URL construction must be
  client-side from the mapped source identity and extension.
- **KNOWN:** Core must not contain Xtream field names or Xtream DTO types.
- **ASSUMED:** `Channel` is the first catalog item needed for Live-only; keeping
  `StreamSource` independently shaped avoids making future M3U or other providers
  fit Xtream's response model.
- **ASSUMED:** `Metadata` is bounded and optional. It is not a raw JSON escape hatch.
- **NEEDS SPIKE:** Exact title-cleaning/display normalization rules for WinUI and
  mixed Arabic/LTR text; reuse evidence, but validate the Windows text layout.

### Provider boundary

Core owns `ICatalogProvider`, with catalog-only operations such as:

- `AuthenticateAsync(ProviderConnection, CancellationToken)` returning a neutral
  `ProviderAccount`/capability result;
- `GetChannelGroupsAsync(ProviderAccount, CancellationToken)`;
- `GetChannelsAsync(ProviderAccount, string? groupId, CancellationToken)`.

`ProviderConnection` is an in-memory request value containing endpoint, username,
and password/secret. It is never persisted, logged, or placed on a domain entity.
The interface returns Core models and neutral failures, not HTTP responses or DTOs.

`XtreamCatalogProvider` lives in Infrastructure. It owns URL normalization,
request construction, JSON DTOs, tolerant string/number parsing, `ext` versus
`container_extension` mapping, status/authentication interpretation, and redacted
diagnostics. It produces `ChannelGroup`, `Channel`, and `StreamSource` only after
mapping and validation.

- **KNOWN:** EPG is excluded from `ICatalogProvider` for this slice.
- **KNOWN:** A later `IEpgProvider` can expose neutral `EpgEvent`/schedule contracts
  independently; catalog and EPG are not forced into one provider type.
- **ASSUMED:** Authentication is part of the connection/catalog boundary because
  the slice needs to validate credentials, but EPG will receive its own boundary
  rather than inherit catalog methods.
- **NEEDS SPIKE:** Whether the target panels need additional tolerant parsing cases
  beyond the Phase A fixtures; add contract fixtures when discovered.

## 3. Infrastructure design

SQLite is an implementation detail of Infrastructure. Repositories expose Core
interfaces/models and keep account scoping in every persisted catalog key. The
spike only needs the Live catalog tables and sync metadata necessary to demonstrate
the vertical slice; no speculative VOD/series schema is required.

The URL builder is a small Infrastructure service with focused tests. It must
normalize scheme, host, port, path joining, IPv6 formatting, and URL encoding, and
must provide a redacted representation for logs. It never treats `direct_source`
as authoritative when it is empty.

- **KNOWN:** No hostname, port, provider name, or account detail is hardcoded.
- **KNOWN:** Cleartext HTTP is deliberately supported for panels that require it;
  TLS certificate validation and system trust anchors remain enabled.
- **ASSUMED:** SQLite migrations are explicit from the first schema version; this
  spike does not use destructive fallback migration.

## 4. Playback architecture

The runtime shape is:

```text
TvivoPlayerControl (App; owns visual composition and host selection)
        |
PlaybackService / PlaybackSession (Core-facing orchestration)
        |
PlaybackRouter (preferred engine, fallback, cancellation policy)
        |
  ┌──────────────────────────────┬─────────────────────────────┐
  │ WindowsPlaybackEngine        │ VlcPlaybackEngine            │
  │ MediaPlayer +                │ LibVLCSharp 3.10.1 +         │
  │ MediaPlayerElement           │ VideoView                     │
  └──────────────────────────────┴─────────────────────────────┘
```

The shared contract is engine-neutral. A `IPlaybackEngine` reports capability,
accepts a `StreamSource`/playback request plus a session token, and returns a
`PlaybackAttemptResult` while publishing state/progress/error events carrying the
same token. The contract does not expose `MediaPlayer`, `MediaPlayerElement`,
`LibVLC`, or `VideoView` to Core callers.

`PlaybackAttemptResult` is a finite enum:

`Started`, `FirstFrame`, `Cancelled`, `NetworkFailure`, `UnsupportedMedia`,
`DecodeFailure`, `Timeout`, `HostFailure`, `UnknownFailure`.

The result is terminal for one attempt. `FirstFrame` means the engine has met the
heuristic below, not that either vendor API supplied a formal first-frame event.
Failures are deliberately coarse and normalized; diagnostic detail stays behind
the adapter boundary and is redacted.

- **KNOWN:** Neither engine supplies a clean common first-frame event.
- **KNOWN:** Native rendering uses `MediaPlayerElement`.
- **KNOWN:** VLC rendering uses `LibVLCSharp.WinUI` `VideoView`.
- **KNOWN:** These hosts do not need to share one physical control type. The App
  owns a host slot/visual state, and the selected adapter attaches its own native
  control; a common interface is enough.
- **KNOWN:** The prior libmpv render-API failure makes a shared render surface an
  unsafe assumption. This design uses native host embedding per engine.
- **ASSUMED:** `TvivoPlayerControl` can switch the displayed host only between
  attempts, not while an engine is actively rendering. The old host is detached
  during terminal cleanup before the alternate is attached.
- **NEEDS SPIKE:** Exact WinUI lifetime, HWND/native-child ownership, DPI, z-order,
  resize, and teardown behavior for each host.

### First-frame heuristics

Windows native engine:

- observe MediaPlayer state reaching a playable/playing state;
- require non-zero natural video width and height (or equivalent video track
  dimensions) from the media properties;
- require the observation to arrive before a bounded startup deadline;
- report `FirstFrame` once and ignore later duplicate state notifications.

VLC engine:

- observe `Playing`/equivalent playback state;
- require non-zero video dimensions from the VLC media/player video output, or a
  vout/frame callback if the binding exposes one reliably;
- use the same bounded startup deadline and one-shot transition.

- **KNOWN:** State alone is insufficient because a stream can enter Playing while
  no picture is visible.
- **KNOWN:** Dimensions/vout evidence is the required heuristic direction from
  Phase B.
- **NEEDS SPIKE:** Which exact Windows MediaPlayer property/event and which exact
  LibVLCSharp callback are reliable on the target SDK/package combination. The
  adapter must hide that decision and tests must not assert an undocumented event.

### Generation/session-token protection

`PlaybackService` creates a monotonically increasing `long generation` for every
playback attempt. It also creates an opaque `PlaybackSessionToken` containing the
generation and a unique session identifier. Every event subscription, timer,
callback, and continuation captures that token.

On stop, cancellation, navigation away, or a new attempt:

1. atomically mark the old session terminal/cancelled;
2. increment generation and publish the new token;
3. unsubscribe/release the old engine and host;
4. accept an incoming event only if its token equals the current token and the
   session is not terminal;
5. dispose callbacks/timers after engine release.

The compare-and-ignore guard is required even after unsubscribe because native
callbacks can arrive late. No callback is allowed to mutate UI state, fallback
state, resume state, or diagnostics after its token is stale.

- **KNOWN:** This directly carries forward the existing generation-counter lesson
  from late mpv playback callbacks.
- **ASSUMED:** A single playback service serializes session transitions; adapters
  may raise events from arbitrary threads, but state publication is marshalled to
  the service's chosen synchronization context.
- **NEEDS SPIKE:** Actual callback threading and shutdown ordering for both native
  packages, including repeated local-fixture start/stop cycles.

## 5. Automatic fallback policy

The router receives a preferred engine and an alternate engine. It makes at most
two attempts for one user play request:

1. start the preferred engine;
2. if it reaches `FirstFrame`, finish successfully;
3. if it returns a clear failure (`NetworkFailure`, `UnsupportedMedia`,
   `DecodeFailure`, `Timeout`, or `HostFailure`), cleanly tear it down and try the
   alternate once;
4. return the alternate result, or the preferred failure if the alternate cannot
   start;
5. never retry after cancellation, and never loop back to the first engine.

Cancellation wins over fallback at every boundary: a cancelled token causes the
router to stop the current engine, suppresses alternate startup, and returns
`Cancelled`. User stop/navigation is not reported as a playback error.

- **KNOWN:** There must be no infinite fallback loop.
- **KNOWN:** Cancellation must always win, including during a late failure callback.
- **ASSUMED:** Only clear, terminal failures trigger fallback. A transient
  buffering/progress state is handled by the active session watchdog and does not
  immediately switch engines.
- **NEEDS SPIKE:** Timeouts and watchdog thresholds after local-fixture evidence;
  choose conservative bounded values rather than tuning against one provider stream.

## 6. Security and credentials

Infrastructure owns `ICredentialStore` and its DPAPI implementation. DPAPI protects
the serialized payload for the current Windows user (or explicitly selected
machine scope only if the deployment requirement later proves it necessary). The
plaintext exists only in memory for the request and is cleared/disposed where the
chosen .NET representation permits.

Persisted envelope:

```text
magic: "TVIVO-CREDENTIALS"
formatVersion: 1
scope: "CurrentUser"
payload: DPAPI-protected bytes
```

The protected payload contains endpoint, username, password, and any required
non-secret account metadata. The envelope is versioned so a future format can be
recognized without trying to deserialize arbitrary bytes as credentials.

Load behavior:

- missing file: treat as signed out;
- unknown magic/version/scope: treat as unusable and require sign-in;
- malformed envelope or JSON: quarantine/replace the corrupt file and require
  sign-in, without logging its contents;
- DPAPI unprotect failure: report a recoverable credential-store error, preserve no
  plaintext, and require sign-in; do not crash-loop;
- successful load: validate required fields and return a redacted account summary.

Writes are atomic: write a new protected file, flush/close it, then replace the
previous file using the platform-safe replace strategy. No backup or diagnostic
export includes the protected blob unless explicitly designed later.

Logging rules:

- never log password, username, full endpoint, query strings, authorization data,
  raw exception messages, or complete playback URLs;
- URL logs use scheme plus redacted host/port/path, with credential path segments
  replaced by placeholders;
- account logs use `AccountId` or a short hash, not identifying credentials;
- exception normalization occurs before diagnostics are emitted.

- **KNOWN:** Credentials must be encrypted at rest and the public repository must
  contain no real account details.
- **KNOWN:** No TLS downgrade or trust-all certificate workaround is allowed.
- **ASSUMED:** Current-user DPAPI is the right desktop-user model for the spike.
- **ASSUMED:** Corrupt credentials are recoverable by re-authentication; the app
  should not silently delete a valid-looking file before quarantine/diagnostic
  handling is complete.
- **NEEDS SPIKE:** DPAPI behavior under roaming profile, account change, and
  uninstall/reinstall boundaries on the intended Windows packaging model.

## 7. Test plan

### Unit tests

`Tvivo.Core.Tests`

- domain invariants and opaque string IDs;
- playback session-token equality/staleness behavior;
- cancellation/result state transitions where they are Core-owned.

`Tvivo.Infrastructure.Tests`

- URL construction for HTTP/HTTPS, explicit/non-standard ports, path joining,
  IPv6, URL encoding, and live `ext` mapping;
- URL and exception redaction, including credentials in path/query/message;
- Xtream DTO-to-domain mapping with quoted/numeric values, missing optional fields,
  empty `direct_source`, and string IDs;
- DPAPI credential envelope versioning, malformed/corrupt payload handling, and
  required-field validation (using test-provided temporary storage, never real
  credentials);
- SQLite account scoping and basic catalog persistence/migration behavior.

`Tvivo.Playback.Tests`

- router preferred-engine selection;
- fallback only on clear failure;
- cancellation suppressing fallback;
- stale callbacks ignored after a new generation;
- terminal cleanup and no-infinite-loop behavior;
- normalized coarse error mapping using fake engine events/results;
- heuristic state machines with synthetic dimensions/vout evidence.

`Tvivo.App.Tests`

- composition/view-model behavior around loading, cancellation, and terminal
  playback state;
- host selection state does not assume the two hosts are the same control type.

- **KNOWN:** No automated test may open a real provider stream; the account limit
  and Phase B test constraints make that unsafe.
- **ASSUMED:** Local HTTP fixtures and fake engines are sufficient for contract and
  router tests.

### Manual/integration testing

Requires a local media fixture and, separately, explicit owner approval before any
provider playback attempt:

- native MediaPlayerElement first-visible-frame behavior;
- VLC VideoView first-visible-frame behavior;
- real WinUI layout, resize, DPI, focus, z-order, and teardown;
- repeated play/stop/navigate cycles with no retained native surface or stale UI;
- provider stream compatibility and actual fallback behavior, one controlled run at
  a time because real streams consume the account connection.

- **NEEDS SPIKE:** “First frame visible” is an integration acceptance criterion,
  not something a unit test can prove.
- **NEEDS SPIKE:** Native rendering and failure taxonomy must be observed on the
  target Windows environment; do not infer them from package documentation alone.

## 8. Future-provider/engine sanity check

### Adding M3U as a second provider

Core should not need redesign. `M3uCatalogProvider` would implement
`ICatalogProvider` and map playlist entries into `ChannelGroup`, `Channel`, and
`StreamSource`. M3U-specific fields remain in Infrastructure DTO/parser code.

Potential additions are neutral optional fields (for example a display label or
additional media metadata), not Xtream-shaped fields. If M3U cannot provide a
stable ID, Infrastructure derives a deterministic opaque ID from the playlist
identity and entry data; Core still sees a string.

- **KNOWN:** This works because Core models use opaque IDs, neutral endpoints, and
  normalized stream sources.
- **NEEDS SPIKE:** M3U identity/stability and playlist refresh semantics when that
  provider is actually introduced.

### Adding MPV as a third engine

Core and the router contract should not need redesign. Add `MpvPlaybackEngine` in
Playback, implement the same session-token/event contract, and provide its own
native host strategy. No shared render surface is assumed.

- **KNOWN:** The engine boundary is already adapter-based and the host controls are
  not part of the Core contract.
- **NEEDS SPIKE:** MPV's Windows embedding and input/lifecycle behavior; the prior
  render-API failure means this must be independently proven.

### Adding EPG independent of catalog provider

Core should gain a separate `IEpgProvider` and neutral EPG models (`EpgChannelKey`,
`EpgEvent`, time range), alongside—not inside—`ICatalogProvider`. An EPG provider
can be implemented by Xtream, M3U metadata, XMLTV, or a future standalone source.
The join key should be an optional neutral channel/provider mapping, never an
Xtream category or DTO reference.

- **KNOWN:** Keeping EPG separate avoids forcing every catalog provider to supply
  EPG and avoids coupling schedule refresh to catalog refresh.
- **ASSUMED:** A later EPG contract can be additive to Core without changing the
  existing catalog and playback models.
- **NEEDS SPIKE:** The identity/linking policy between channels and EPG sources
  once a real second source exists.

### Gate 1 conclusion

The proposed Core boundary passes the future-needs check: M3U adds another catalog
implementation, MPV adds another playback adapter/host, and EPG adds a separate
provider contract. None requires Core to learn Xtream DTOs, SQLite, WinUI, VLC, M3U
syntax, or MPV embedding details. The main risks are explicitly isolated as
implementation spikes: native host behavior, first-frame evidence, provider ID
stability, and EPG linking.

## 9. Phase C acceptance criteria

- The plan exists at the requested path and no solution/project/code files are
  created.
- Every production and test project, reference direction, and forbidden Core
  dependency is explicit.
- Domain fields and Xtream quirks are represented without leaking Xtream concepts
  into Core.
- Playback result, heuristic, host, session-token, fallback, and cancellation rules
  are finite and testable.
- Credential versioning/corruption/redaction/TLS rules are explicit.
- Unit versus manual/integration evidence is separated.
- Every material decision is tagged KNOWN, ASSUMED, or NEEDS SPIKE.
- M3U, MPV, and independent EPG additions do not require a Core redesign under the
  proposed contracts.
