# Mini-player feasibility plan (analysis only)

## Recommendation

Feasible as a WinUI 3 secondary XAML `Window` configured as a small always-on-top tool window. The current project targets Windows App SDK 2.5.1, so the WinUI `Window.AppWindow` API is available. Use a normal overlapped presenter with `IsAlwaysOnTop=true` for freely sized, edge-docked behavior; `CompactOverlayPresenter` is the built-in PiP alternative, but its documented sizing surface is only an initial preset size. This is a plan, not implementation authorization.

## Trigger and Issue 5 boundary

The existing Exit cinema control or Escape path while cinema mode is active is the only trigger: exiting cinema opens the mini window and transfers the current video surface while keeping the same playback session alive. It must not be wired into generic `ShowPage` navigation. The existing Player-to-other-page cleanup in `ShowPage` remains the default: ordinary navigation away from Player still invalidates and stops playback. Closing the mini window should return the video surface to the main Player page; it should not silently restart the stream.

## Window APIs

- Create a dedicated WinUI `Window` for mini-player content. Microsoft documents secondary WinUI windows as sharing the app's UI thread, with each XAML tree receiving its own `XamlRoot`.
- Configure its `AppWindow` using an `OverlappedPresenter` (`IsAlwaysOnTop=true`, resizable, minimizable, and with the desired border/title-bar style). This is supported across Windows App SDK versions 1.0 through 2.0 in the API reference, and the project uses 2.5.1.
- `CompactOverlayPresenter` is available and explicitly described as picture-in-picture. It exposes `InitialSize` presets, so it is a candidate if Windows-managed PiP behavior is preferred over exact custom docking/resize behavior.
- Use `DisplayArea.GetFromWindowId` and its `WorkArea`, then `AppWindow.MoveAndResize` to place the window against a display edge. Re-evaluate on display/work-area changes and clamp after manual resize. Those APIs use screen-coordinate `RectInt32` bounds.
- For drag, keep a narrow custom title/drag strip and use normal caption dragging where practical; otherwise handle pointer dragging in the mini chrome and move the AppWindow. Do not continually snap while the pointer is moving. Snap to the selected work-area edge on release, with a small margin; preserve free dragging until then.

References: [WinUI multi-window overview](https://learn.microsoft.com/en-us/windows/apps/develop/ui/multiple-windows), [windowing overview](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windowing-overview), [always-on-top presenter property](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.overlappedpresenter.isalwaysontop?view=windows-app-sdk-2.0), [CompactOverlayPresenter](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.compactoverlaypresenter?view=windows-app-sdk-2.0), [display work area](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.displayarea.workarea?view=windows-app-sdk-1.0), and [MoveAndResize](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.appwindow.moveandresize?view=windows-app-sdk-1.4).

## Keeping the stream alive

Do not call `PlaybackService.PlayAsync` again, `StopAsync`, or switch engines during the handoff. Keep the active `IPlaybackEngine`, `PlaybackSessionToken`, and source unchanged; this avoids a second connection and avoids a playback restart. Transfer only the video presentation surface to the mini window, leaving the main Player page and its ordinary teardown path intact. Closing the mini window moves that same surface back.

The current playback controls are owned by `MainWindow`; decide explicitly whether controls move with the surface or remain reachable from the main Player page. Keep status, seek, pause, and volume wired to the same `_engine` instance. Do not duplicate player objects or create an independent stream for the secondary window.

## Engine-specific feasibility and risks

- **FFmpegInteropPlaybackEngine:** It owns one `Windows.Media.Playback.MediaPlayer`; `MainWindow` currently binds that object to one `MediaPlayerElement`. Rebind the same player to a mini-window `MediaPlayerElement` while the source and playback state remain untouched. Validate that reparenting the player element between distinct XAML roots preserves audio, video, time, and pause/seek state on target Windows builds. Do not dispose/recreate the `MediaPlayer` or `FFmpegMediaSource`.
- **WindowsPlaybackEngine / LibVLC:** Despite its historical class name, the current implementation is `VlcPlaybackEngine`. It owns a LibVLC `MediaPlayer` and a single initialized `VideoView`; `StartAsync` assigns `View.MediaPlayer`, and stop detaches it. Prefer moving/reparenting that same `VideoView` to the secondary XAML window, retaining the existing player and native output. The current engine caches one `_view`, and initialization passes swap-chain options from the initialized view into LibVLC. A second independently initialized `VideoView` is therefore not a safe assumption. Rehosting the same WinUI control across `XamlRoot`s and preserving the LibVLC swap-chain output is the largest feasibility risk; if it blanks or tears down output, stop before attempting a restart-based workaround because that would interrupt playback.
- These engines render through different surfaces. A shared mini-window shell is practical, but surface transfer needs separate validation for each selected engine. Do not promise parity until both pass.

## Rough implementation sequence (pending approval)

1. Define the explicit cinema-exit transition and state ownership. Keep normal Player navigation routed through the existing teardown untouched; mini mode must not be entered from `ShowPage` or `StopPlaybackForNavigation`.
2. Add a secondary mini-player `Window` with minimal title/drag strip, close/restore controls, and a video host. Apply the overlapped always-on-top presenter and work-area placement.
3. Implement one surface-transfer adapter per engine. Detach from the main visual tree before attach to the mini tree; on close, reverse the transfer. Do not call playback start/stop or create another player.
4. Keep transport and metadata commands against the existing `_engine`, and define behavior for closing the main window while mini mode is open (close both and stop through the existing lifecycle cleanup).
5. Add edge snap on drag completion, free resize with minimum aspect-preserving video size, monitor/work-area change handling, and bounds clamping. Persist last dock edge/size only if that is already an accepted preferences pattern.
6. Verify separately with local fixture playback on Native/FFmpegInterop and LibVLC: observe continuous moving frames and monotonic time through transfer and return, no second connection, controls, close behavior, DPI/multiple displays, and normal navigation-away still stopping playback. Playback validation requires explicit approval under the project's existing gate.

## Main uncertainty / next gate

The WinUI windowing APIs make topmost positioning and multiple windows feasible. Whether the existing LibVLC `VideoView` and MediaPlayerElement surfaces can be rehosted across XAML roots without interrupting their active playback is not established by source inspection or API documentation. The next gate is approval for an isolated surface-transfer spike with both engines, before building the full mini-player experience.
