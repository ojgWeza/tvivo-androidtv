# Tvivo.App hang investigation — PID 91720

## VERDICT

The captured freeze is **UI-thread saturation inside native WinUI XAML work**. Thread 77308 consumed essentially one full CPU core while it processed XAML/DirectWrite and heap activity. The catalog page had a very large live shelf visual tree: 110 currently wired shelf `GridView`s (111 managed wrappers including the open-shelf grid). This is the strongest supported explanation for slow mode changes, lagging scroll, and clicks that appear to do nothing: the UI message loop cannot process input promptly while it is busy with the tree. The precise WinUI internal operation and the trigger for the earlier native worker-thread burst remain unproved.

## STRONGEST EVIDENCE

- Full memory dumps were captured before stopping the app: `D:\Temp\TvivoHang\PID-91720-20260926\hang-91720-20260926-130413.dmp` (2,075,378,046 bytes) and `hang-91720-20260926-second.dmp` (2,074,025,039 bytes). Raw native stacks, managed heap statistics, page fields, collection fields, and thread CSVs are beside them. Dumps may contain account data; keep them out of the public repo.
- At first contact the app had `Responding=False`, 446 threads, about 1,451 MiB working set, and 1,377 process CPU seconds. A later five-second sample recorded **5,046.9 ms on UI thread 77308** and **5,093.8 ms for the entire process**; every other sampled thread was effectively idle. UI thread 77308 had accumulated over 1,659 CPU seconds by then. The process briefly reported `Responding=True` later, consistent with intermittent recovery, but continued consuming a full core.
- Native stack grouping in the first dump: **424 of 446 threads** shared the idle `ntdll!ZwWaitForWorkViaWorkerFactory` signature. The remaining 22 were UI, CLR, compositor, messaging, timer, and other threads. OS wait-reason sampling found 426 `EventPairLow` waits. The CLR portable thread pool reported one idle worker in dump 1 and zero in dump 2. These 424 threads were native Windows worker-factory threads, not 424 blocked .NET workers. Thread creation times cluster at 12:35 (111) and 12:36 (259), with 18 more at 12:46 and 16 at 12:54. Their original work cannot be recovered from idle stacks.
- The UI native stack in dump 1 was in `ntdll!RtlAllocateHeap`/`RtlFreeHeap`, reached through `Microsoft_UI_Xaml` while handling a window message. In dump 2 it was in `ucrtbase` allocation and `DWrite`, reached through many recursive `Microsoft_UI_Xaml+0x65f1a` frames. Neither sample shows a managed catalog method or SQLite call on the UI thread. Public symbols do not identify the WinUI internal function at that offset.
- Both managed heap snapshots contained exactly **1 `CatalogLandingPage`, 1 `MainWindow`, 111 `GridView` wrappers, 229 `CatalogShelf` objects, 2,663 `CatalogCard` objects, 1 managed `Image` wrapper, 0 managed `BitmapImage` wrappers, and 1 `DispatcherTimer`**. The second page state was Series mode, no open shelf, interaction marked ready, and first load complete. Its grid wiring set had 238 allocated slots minus 128 free slots = **110 live grids**. The page held two cached snapshots, four refresh-freshness marks, and **zero active refresh tasks** (dictionary count 1, free count 1). Managed heaps were only 7.93 MB and 7.78 MB, whereas the process later held about 1,356 MiB private bytes and 1,959 MiB working set. Most memory is native or otherwise outside the managed heap; exact owners are unknown.
- Source boundary: `CatalogLandingPage.xaml` uses a nonvirtualizing outer `ItemsControl` inside a `ScrollViewer` for all shelves; each shelf creates a `GridView` with up to 12 cards, an image, a placeholder visual tree, and event handlers. `BuildShelves` builds every category; `RenderShelfSurface` assigns all shelves at once on the UI thread. The inner `ItemsStackPanel` and `ItemsWrapGrid` do not virtualize that outer shelf list. `ReadCatalogSnapshotAsync` puts SQLite reads in `Task.Run`, but `ApplySnapshot`/`RenderShelfSurface` run after the await on the UI thread.

## EXACT BOUNDARY

The direct observation stops at **native WinUI XAML/DirectWrite work monopolizing the UI thread while a large shelf tree is live**. The source and live object counts strongly implicate full shelf materialization and repeated layout/render work. The dump does not prove which XAML operation initiated the long run, whether artwork decode contributed to the native memory and worker surge, or which event caused each pass. Clicking a title during the saturation can wait in the UI queue; the dump cannot prove that the click handler itself is defective.

The sort combo is in a separate auto-sized header row and the loading `ProgressRing` is in the content row. `PrepareMode` requests the loading state, then the page rebuilds shelves. A starved UI thread can delay the visual frame that would show the spinner and reposition content. That is a source-supported explanation for symptom C, **not a dump-confirmed layout root cause**. Capture a startup/mode-switch visual timeline after the performance issue is isolated.

## RULED OUT AT CAPTURE

- **Active refresh loop or stacked refreshes:** zero active refresh tasks; two cached snapshots and four freshness marks. Source deduplicates concurrent refresh per account. This does not exclude earlier unnecessary refreshes.
- **Spotlight rotation timer:** no such timer in the page; Spotlight choice is stable per session/day/mode in source. Rendering Spotlight on snapshot apply may still add work.
- **SQLite read blocking the UI thread:** reads are inside `Task.Run`; neither UI stack contains SQLite. Background catalog queries may contribute to latency on cache misses, but they did not explain the captured full-core UI saturation.
- **Managed thread-pool starvation / sync-over-async causing 446 threads:** CLR workers were one idle, then zero; 424 threads were idle native workers.
- **MainWindow playback timer accumulation:** one `DispatcherTimer` exists, and its tick exits immediately outside the Player page. The captured catalog page was in Series mode.
- **Repeated page-instance leak:** one `CatalogLandingPage` and one `MainWindow` in both dumps. A native XAML or image-resource leak is not ruled out.

## UNCERTAINTY

`dumpheap` sees managed WinRT wrappers, not all native XAML `Image`, `BitmapImage`, decoded bitmap, DirectWrite, or thread-pool objects. The count of one managed `Image` and zero managed `BitmapImage` therefore does **not** rule out artwork loading or decode pressure. The app's `<Image Source="{Binding ArtworkUrl}">` has no decode-width budget, and the Spotlight creates a `BitmapImage` from a remote URI. Artwork and native allocations remain plausible contributors, but the dumps lack allocation stacks or a network/image trace. Likewise, idle worker stacks reveal the thread population, not why Windows created it.

## NEXT GATE

Reproduce under a native CPU/allocation trace with WinUI/DirectWrite and image/network events while recording shelf count, realized shelf/grid/card count, UI-thread frame time, native memory, and native worker count at each mode switch. First isolate the outer shelf `ItemsControl`/`RenderShelfSurface` workload using a bounded or virtualized shelf count in a diagnostic build, then compare the same trace with artwork disabled to separate visual-tree cost from image decode/request cost. Verify symptom C with frame captures during that same run. This handoff makes **no code changes or fix claim**.

PID 91720 and its `winapp run` parent PID 59816 were stopped after both dumps and samples. Follow-up process checks found no `Tvivo.App` or `winapp` process and no children of either PID.
