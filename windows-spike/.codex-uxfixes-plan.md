## Findings and proposals

### 1. Category selection reloads content

**Root cause / evidence.** `MainWindow.ShowCatalogAsync` calls `CatalogLandingPage.LoadAsync` on every navigation (`windows-spike/src/Tvivo.App/MainWindow.xaml.cs:143-155`). `LoadAsync` always enters `LoadCatalogAsync` (`CatalogLandingPage.xaml.cs:125-143`); that method reads a snapshot from SQLite, then unconditionally refreshes the account from the provider, then reads and applies another snapshot (`CatalogLandingPage.xaml.cs:185-217`). `SetModeAsync` reads cached content (`:101-108`), but the shell navigation bypasses it. The existing cache is SQLite, not an in-memory per-mode snapshot cache.

**Proposed approach.** Keep SQLite as durable source of truth; add a bounded in-memory snapshot cache keyed by account identity, mode, selected group, filter, sort, and page/offset. On mode return, immediately reapply the matching snapshot without resetting interaction state. Separate cache display from refresh policy: refresh on initial load, explicit retry/refresh, or a defined freshness interval, and refresh asynchronously without making every category click look like a reload. Invalidate relevant entries after refresh, account changes, and mutations.

**Risk / complexity.** Medium. Snapshot keys and invalidation must include every query dimension; stale search/group/page results are the main correctness risk. Memory should be bounded because catalogs can be large.

**Dependencies.** Independent of items 2–8. Can share the catalog snapshot boundary with item 2.

### 2. Spotlight repeats one title and artwork is unreliable

**Root cause / evidence.** `RenderSpotlight` deterministically chooses the first card in the first shelf (`CatalogLandingPage.xaml.cs:436-452`). Shelf construction makes the recently-added shelf first and preserves repository order (`:300-338`), so this is not a rotating selection. The checked-in Spotlight XAML has only a gradient and `SpotlightInitials`; it contains no image control or artwork binding (`CatalogLandingPage.xaml:249-278`). Card tiles do bind `ArtworkUrl` to an `Image` (`:14-35`), and `ToCard` sources it from `channel.LogoUri` (`CatalogLandingPage.xaml.cs:373-380`). Thus the reported hero image failure is not reproducible from this source version: it may describe the tile artwork or a different tested build.

**Proposed approach.** Define a stable, bounded rotation policy over eligible movie/series cards (for example, choose a different deterministic candidate per app session/day, avoiding immediate repeats), rather than choosing the first card. Add an actual Spotlight artwork image bound to the selected card URL. Use a load-failure-aware presentation state and fall back to item 3’s Tvivo artwork. Do not rotate on every page re-render, which would make navigation feel random.

**Risk / complexity.** Medium. Rotation needs an explicit product rule and must remain stable during one session. Image availability, malformed URLs, and navigation timing need coverage.

**Dependencies.** Shares the image fallback component/state with item 3. Cache changes in item 1 should not determine the rotation algorithm, though the candidate list comes from catalog data.

### 3. Replace title initials on failed artwork

**Root cause / evidence.** The tile template places `TextBlock Initials` beneath an `Image` with no `ImageFailed`/visibility state (`CatalogLandingPage.xaml:14-35`). Initials are computed by taking the first character of up to two words (`CatalogLandingPage.xaml.cs:403-408`). That intentionally exposes title-derived letters when the image is absent, but can look arbitrary. The reported single “X” for a multiword title does not match this exact helper, which would produce two letters; verify the tested binary/source revision before implementation.

**Proposed approach.** Replace title-derived initials with one reusable Tvivo placeholder: a branded abstract screen/film glyph in a restrained gradient tile, implemented as local vector/XAML resources so it has no network dependency. Keep it visible until image success, hide it only after successful load, and restore it on image failure. Reuse the same visual for Spotlight at its larger aspect ratio. Avoid title fragments as fallback content.

**Risk / complexity.** Low to medium. Visual consistency and correct load/failure transitions are the main concerns; use a local asset or vector resource rather than a remotely loaded logo.

**Dependencies.** Shared fallback state/component with item 2. No catalog or windowing dependency.

### 4. Movie selection reports timeout before the user presses Play

**Root cause / evidence.** The selection handler already opens Player and starts playback (`MainWindow.xaml.cs:231-250`); `StartPlaybackAsync` calls `PlaybackService.PlayAsync` (`:252-284`). Both engines call their play operation during `StartAsync`: native `MediaPlayer.Play()` (`Tvivo.Playback/FFmpegInteropPlaybackEngine.cs:72-91`) and LibVLC `player.Play()` (`Tvivo.Playback/WindowsPlaybackEngine.cs:111-159`). The manual Play button retries `StartPlaybackAsync` only after the current attempt is no longer active (`MainWindow.xaml.cs:319-329`). The likely failure is therefore startup readiness/first-frame detection timing out and cleanup stopping the first attempt, after which a new manual attempt succeeds—not a missing autostart call. Native startup waits up to 30 seconds for `MediaOpened` (`FFmpegInteropPlaybackEngine.cs:9, 68-91, 137-141`); LibVLC waits up to 10 seconds for its readiness/first-frame condition (`WindowsPlaybackEngine.cs:30, 90-100, 132-164`). The selected engine is preference-controlled (`MainWindow.xaml.cs:43-45`), so the exact timeout path is not established by source alone.

**Proposed approach.** Reproduce separately for each engine with the same local fixture and capture selected engine, state transitions, timeout source, and whether frames/media-open arrive. Correct the signal/deadline/dispatcher handling that causes the false timeout; keep the existing single autostart invocation. Ensure a timeout does not silently destroy a session that is already rendering, and present a retry only for genuine startup failure. Avoid starting a second stream concurrently.

**Risk / complexity.** High. Engine callbacks, UI-thread affinity, startup cleanup, and late events can race; playback paths need manual validation with the project’s approved fixture procedure.

**Dependencies.** Independent of window chrome and catalog. Runtime diagnosis must identify the selected engine before selecting a narrow fix.

### 5. Cinema mode should cover the PC screen

**Root cause / evidence.** `SetCinemaMode` hides the app header, sets the content row to zero height, and removes player details/transport (`MainWindow.xaml.cs:432-459`). It never changes the window presenter, bounds, or display area. Cinema currently means an in-window layout mode, not fullscreen.

**Proposed approach.** Define cinema mode as a true borderless fullscreen window on the current display, with a reversible transition that stores the previous presenter/bounds and restores them on exit. Preserve the playback surface/session through the transition. If product intent is instead “video fills the app window,” rename/document the mode; the user report favors true fullscreen.

**Risk / complexity.** Medium-high. Window state restoration, DPI, monitor changes, taskbar behavior, and custom titlebar visibility interact. Validate playback remains continuous during presenter transitions.

**Dependencies.** Implement after the fullscreen state machinery in item 7 and coordinate with the custom titlebar in item 6. Item 8 supplies reliable exit paths.

### 6. Replace the default Windows title bar with Tvivo chrome

**Root cause / evidence.** `MainWindow.xaml` starts with a standard `Window` and app content, with no titlebar extension or app-owned titlebar region (`MainWindow.xaml:1-12`). `MainWindow.xaml.cs` contains no `ExtendsContentIntoTitleBar`, `SetTitleBar`, or caption-button setup (reviewed file; relevant window setup is `:36-65`). This leaves the native default titlebar visible.

**Proposed approach.** Add an app-owned top chrome region with Tvivo identity, minimize and close buttons, and a compact-mode button that is only a hook for the separate future mini-player feature. Retain native caption-button/system behaviors where possible through WinUI titlebar APIs, and define a draggable area that excludes buttons and interactive navigation. Hide/restore this chrome consistently during fullscreen cinema. Do not build compact playback behavior in this batch.

**Risk / complexity.** Medium. Custom caption controls need correct hit testing, keyboard accessibility, window dragging, and consistent layout across scale factors.

**Dependencies.** Coordinate with items 5 and 7: fullscreen state must hide custom chrome and restore it; launch-fullscreen behavior must start in the matching chrome state. The compact button has no dependency on mini-player implementation and remains inert or explicitly unavailable until that feature is approved.

### 7. Allow startup in fullscreen

**Root cause / evidence.** `App.OnLaunched` constructs and activates `MainWindow` without applying a presenter or saved startup preference (`App.xaml.cs:57-65`). No fullscreen/presenter setup appears in the window constructor (`MainWindow.xaml.cs:36-65`).

**Proposed approach.** Add a small window-state abstraction that can apply normal/windowed and fullscreen modes at launch and later. Choose and document the default (recommend a persisted user preference, defaulting to windowed), then apply it before/at activation without conflating “app starts fullscreen” with “player is in cinema mode.” Use the same state abstraction for item 5 so enter/exit logic is centralized.

**Risk / complexity.** Medium. Initial activation timing and saved display bounds can produce off-screen or flickering windows if applied in the wrong order.

**Dependencies.** Foundation for item 5 and should be designed alongside item 6. It does not itself imply cinema mode or hide/show the custom app header unless the selected startup state explicitly requests cinema.

### 8. Make cinema mode easy to exit

**Root cause / evidence.** Escape handling exists in `PlayerPage_KeyDown` and calls `SetCinemaMode(false)` (`MainWindow.xaml.cs:418-430`), but it depends on the key event reaching `PlayerPage`; a focused child/native video surface may prevent that route. The video controls expose no double-tap/double-click handler (`MainWindow.xaml:104, 118-126`). The cinema layout collapses the visible controls (`MainWindow.xaml.cs:443-459`), leaving no visible exit button. This explains how the current escape implementation can exist while the user still cannot exit reliably.

**Proposed approach.** Keep Escape as a window-level/accelerator route active whenever cinema is on, independent of focused child control. Add a double-click/double-tap gesture on the video surface to toggle cinema, with pointer event handling that does not swallow ordinary clicks or transport actions. Keep a discoverable exit affordance available on pointer movement if product design supports an overlay; at minimum support both requested gestures. Restore focus sensibly after exit.

**Risk / complexity.** Medium. LibVLC/native video surfaces may consume pointer/key input outside normal XAML routing; test both playback engines and keyboard focus locations.

**Dependencies.** Depends on a single explicit cinema state from item 5. Coordinate gesture and keyboard handling with the custom titlebar/window-level keyboard routing in item 6.

## Suggested implementation batches

1. **Catalog return and artwork (items 1–3):** add keyed in-memory snapshots and a deliberate refresh policy; select a stable rotating Spotlight candidate; implement one Tvivo fallback presentation for tile and hero images. Confirm whether the tested build contains a hero image before treating that report as an image-loader defect.
2. **Autostart reliability (item 4):** first reproduce by engine and establish the timeout signal; then fix only the startup path that reports false failure. Preserve the existing automatic `StartPlaybackAsync` call.
3. **Window state and chrome foundation (items 7 and 6):** define normal/fullscreen state, startup preference, custom titlebar controls, and drag/caption behavior together.
4. **Cinema and exit behavior (items 5 and 8):** make cinema apply true fullscreen through the shared window state; add reliable window-level Escape and video double-click/double-tap exit. Confirm state restoration and continuous playback.
