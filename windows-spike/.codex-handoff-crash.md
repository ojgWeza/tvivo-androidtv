# WinUI startup crash investigation — fullscreen A/B and Win32 replacement

## Title-bar isolation and proposed fix (2026-09-26)

### VERDICT

With startup fullscreen enabled in every run, the default native title bar survived 3/3 launches for over 20 seconds each. Adding only `ExtendsContentIntoTitleBar = true` crashed on the first launch with `0xC0000374` before activation. An additional arm that kept native title-bar extension off but called `OverlappedPresenter.SetBorderAndTitleBar(true, false)` also crashed on its first launch. This makes the custom WinUI title-bar setup incompatible with the startup Win32 fullscreen style transition in this environment. The proposed source fix removes `ExtendsContentIntoTitleBar`, `SetTitleBar`, and caption-button hiding. Tvivo's own controls remain; its drag region now starts a Win32 caption drag. The native caption buttons remain visible in windowed mode because hiding them also reproduced the crash.

### STRONGEST EVIDENCE

| Arm | Fullscreen | Result | Window/process observation |
| --- | --- | --- | --- |
| 1: native title bar, no custom title-bar calls | Enabled | 3/3 no crash | All activated; nonzero window handle and `Responding=True` for 20+ seconds; each stopped deliberately and gone afterward |
| 2: `ExtendsContentIntoTitleBar` only | Enabled | 1/1 `0xC0000374` | No activation or nonzero window handle sampled; PID 49336 gone after crash triage |
| 5: native extension off, caption hiding on | Enabled | 1/1 `0xC0000374` | No activation or nonzero window handle sampled; PID 47944 gone after crash triage |
| Final source, native title bar plus custom-region Win32 drag | Enabled | 1/1 no crash | Built with zero warnings/errors, activated; PID 59812 had nonzero handle and `Responding=True` in 11 two-second samples, then was stopped and gone |

The temporary switch was `TVIVO_TB_MODE`. Mode 1 sampled PIDs 96676, 68908, and 76648. Mode 2's fatal log is `C:\Users\Dell\AppData\Local\Temp\winapp-dumps\debug-49336-20260926-122427.log` and dump is `crash-49336-20260926-122429.dmp`; mode 5's dump is `crash-47944-20260926-122846.dmp`. The per-run CLI logs and approximately two-second process samples for mode 1 runs 2–3 and modes 2/5 are in `D:\Temp\TvivoTitleBarAB\`. Mode 1 run 1 and the final-source run were sampled directly in the shell. All launches used `winapp run ./src/Tvivo.App/Tvivo.App.csproj --arch x64 --debug-output`. No stream was opened.

### EXACT BOUNDARY

In mode 2, the constructor logged the selected mode, completed, then failed inside `WindowStateController.SetStyle` → `SetWindowLongPtrW` during pre-activation fullscreen. `SetTitleBar` and `OverlappedPresenter.SetBorderAndTitleBar` were absent in that arm. The debug log reports a previously freed heap block modified at offset `0x6c`, followed by fatal `0xC0000374`. The managed fatal thread points to `WindowStateController.SetStyle` (`:123`) → `Apply` (`:60`) → `MainWindow.PrepareForActivation` (`:89`) → `App.OnLaunched` (`:63`). The earlier dump analysis identifies native `CTitleBar` teardown on this style transition; no native stack was extracted from the new mode 2 dump.

### RULED OUT

- Startup fullscreen alone is insufficient for this crash: mode 1 kept the same fullscreen transition and survived 3/3 runs.
- `SetTitleBar` and caption hiding are not required for the mode 2 crash; neither ran in that arm.
- `ExtendsContentIntoTitleBar` is not required for the mode 5 crash; only caption hiding was added to the otherwise stable native-title-bar configuration.
- The caught SQLite `0x80073D54` first-chance exception still occurred in stable and crashing arms, so it does not distinguish this failure.

### UNCERTAINTY

The tests locate the incompatible title-bar operations but do not prove the instruction that first corrupts the heap. Full page heap was not run: `gflags.exe` was absent from PATH, the installed Windows Kits locations, the WinApp debugger files, and searched tool locations. Therefore there is no allocation/free stack for the corrupted block. The app's actual pixels and drag/minimize/close/fullscreen interactions were not driven; process handle and Windows `Responding` status establish startup liveness only. Native caption buttons are visible in windowed mode. Arms 3 and 4 were skipped because mode 2 already established the first failing boundary; the earlier full-setup baseline crashed repeatedly as documented below. The temporary mode 5 was a focused check of whether caption hiding could be retained.

### NEXT GATE

Use a machine with `gflags`/Debugging Tools to enable full page heap for `Tvivo.App.exe`, repeat the original full-title-bar baseline once, extract `!heap -p -a` allocation/free history if present, and disable page heap immediately afterward. Separately validate the proposed native-title-bar source visually and exercise Tvivo drag, minimize, close, and fullscreen toggle in an approved UI pass. `TVIVO_TB_MODE` was removed from source; no Tvivo.App or winapp process remained at handoff, and no `Tvivo.App.exe` Image File Execution Options registry key was present (page heap was not enabled).

## Post-replacement forensic update (2026-09-26)

### VERDICT

The Win32 borderless fullscreen replacement also crashes before activation. In the new PID 60412 dump, the managed call is `WindowStateController.Apply` → `SetStyle` → `SetWindowLongPtrW`, **not** `SetWindowPos` or an `AppWindow.SetPresenter` call. The native failure occurs when that style change delivers `WM_STYLECHANGED` (`0x7d`) to Microsoft UI Windowing: its titlebar feature uninitializes and destroys `CTitleBar`, and `RtlpCoalesceFreeBlocks` detects an already-corrupted free-list entry during that teardown. This is the detection/free boundary; the dump does not identify the earlier write or prove which constructor-time titlebar operation, if any, caused it.

### STRONGEST EVIDENCE

- New artifacts: `C:\Users\Dell\AppData\Local\Temp\winapp-dumps\crash-60412-20260926-121312.dmp` (full-memory user dump) and `debug-60412-20260926-121309.log`. The log records `MainWindow constructor completed` at 12:13:12.892, then `HEAP: Free Heap block 0000017A09578C10 modified at 0000017A09578C7C after it was freed`, then second-chance `0xC0000374`. There is no `startup window state applied` or `MainWindow activated` line.
- The dump's managed thread is `App.OnLaunched` (`App.xaml.cs:63`) → `MainWindow.PrepareForActivation` (`MainWindow.xaml.cs:84`) → `WindowStateController.Apply` (`WindowStateController.cs:57`) → `SetStyle` (`:120`) → P/Invoke. The source at `:57` calls `SetStyle(fullscreenStyle)`; the subsequent `SetBounds`/`SetWindowPos` has not been reached.
- The native stack is `user32!_SetWindowLongPtr` → `win32u!NtUserSetWindowLongPtr` → User32 window-message dispatch → `Microsoft_UI_Windowing_Core!Windowing::Window::ProcessMessage` (`0x7d`) → `AppWindowTitleBarFeature::FeatureProc` → `AppWindowTitleBar::EvaluateNativeInitialization` → `UninitializeTitleBarNative` → `CTitleBar` destructor → `wil::details::event_watcher_state` destructor → `RtlFreeHeap` → `RtlpCoalesceFreeBlocks` → `RtlReportFatalFailure`. The earlier `crash-6196-20260926-111528.dmp` and A1 `crash-73716-20260926-114804.dmp` show the same `CTitleBar` teardown and heap-coalescing path, reached through `AppWindow.SetPresenter` instead of `SetWindowLongPtrW`.
- The A/B skip arm used the same binary as its pre-activation fullscreen arm and logged `A/B: startup fullscreen skipped` after `MainWindow constructor completed`, then activation. All three B runs had nonzero, responsive window handles for at least 18 seconds. Thus they still ran `InitializeComponent`, `ExtendsContentIntoTitleBar = true`, `SetTitleBar(TitleBarDragRegion)`, `WindowStateController` construction, `AppWindow.GetFromWindowId`, and `OverlappedPresenter.SetBorderAndTitleBar(true, false)`; they skipped the startup fullscreen call/transition. The original B-arm source was reverted, so its exact conditional body is not retained; these are the operations established by shared constructor source, A/B logs, and the prior handoff.
- In CDB, `!heap -x 0000017A09578C10` identifies a `0xb0`-byte **free** block on heap `0000017A46960000`, with a corrupt list link (`Blink->Flink != Block`). `!heap -p -a` on the block/header provides no page-heap allocation or free stack. `!gflag` is `0x70` (tail, free, and parameter checking), without full page heap. The heap diagnostic identifies corruption of a previously freed block, not its allocator/owner or the instruction that changed it.

### EXACT BOUNDARY

The common observed failure is **native titlebar uninitialization during a window-state/style transition**, before `Activate()` in the original A arm and Win32 replacement; C reached activation and then failed in the same titlebar teardown after its queued presenter transition. The Win32 attempt passed constructor-time titlebar setup, entered `PrepareForActivation`, read placement/bounds/style/monitor, and failed during the style write's synchronous message handling. It did not reach fullscreen bounds placement or display a validated window. The three B runs avoided that transition; they do not show whether the heap had already been corrupted but unexamined, or whether the transition itself caused the invalid write/free.

### RULED OUT

- `AppWindow.SetPresenter` is not required to reproduce the fatal crash; the replacement contains no such transition.
- `SetWindowPos` fullscreen placement and `Activate()` are after the new failing call, so neither is the immediate new trigger.
- Constructor-time `ExtendsContentIntoTitleBar`, `SetTitleBar`, caption-button hiding through `OverlappedPresenter`, and initial `WindowStateController` HWND/`AppWindow` access are **not individually sufficient to crash on startup**: the B arm ran them and remained responsive. Their interaction with later titlebar teardown remains possible.
- The caught `0x80073D54` SQLite/no-package-identity first-chance exception appears in the new debug log before the fatal event, as in the stable B runs; the debug log's `TargetInvocationException` analysis refers to that saved first-chance context, not the fatal native stack.

### UNCERTAINTY

The damaged free block has no owner/allocation/free stack in this dump. A late detection at `CTitleBar` destruction does not establish when it was overwritten. A constructor-time mismatch involving XAML titlebar extension, `SetTitleBar`, or caption hiding is plausible, but so is corruption caused during the transition. `!heap -p -a` cannot answer this without page-heap history. The new run has no post-crash process sample in the supplied artifacts. A read-only process check later found no PID 60412 or other `Tvivo.App`/`winapp`/`WerFault` process. Earlier A/C CSVs show crashing app PIDs briefly present with no window, then absent after winapp/WER dump triage; C1 also sampled `WerFault`. This fits a debugger/WER-held crashing process, not an app-owned hidden-window fallback or a healthy 500 MB resident app. The app has no native heap-corruption handler; its `OnLaunched` catch handles managed exceptions only.

### NEXT GATE

No app launch was made for this investigation. The next approved diagnostic run should enable **full page heap with allocation stack traces** for `Tvivo.App.exe`, then repeat one isolated launch and use `!heap -p -a` on the reported block to identify its allocation/free owner and earlier corruption boundary. In that same controlled A/B, keep the window state unchanged while isolating constructor-time titlebar setup (`ExtendsContentIntoTitleBar`/`SetTitleBar`, caption hiding via `OverlappedPresenter`, and initial HWND/`AppWindow` access) one component at a time; compare with the three established skip-fullscreen runs. Do not infer a source fix from the current detection stack alone. Any app launch or deployment requires the owner's explicit approval.

## Earlier fullscreen A/B baseline

## VERDICT

The approved A/B isolates the startup fullscreen presenter transition as the immediate crash trigger in this environment. Applying `AppWindow.SetPresenter(FullScreen)` before `Activate()` crashed 3/3 launches; skipping only that call launched a responsive window for at least 18 seconds in 3/3 launches. Moving the same transition to a `DispatcherQueue` callback after `Activate()` also crashed 3/3 launches. The fatal detection is at `SetPresenter` in both fullscreen arms; the experiment does not prove which earlier native operation corrupted the heap. The post-activation change was unstable and has been reverted. Source code is back to its pre-test state; no environment-variable switch remains.

## STRONGEST EVIDENCE

Each launch used `winapp run ./src/Tvivo.App/Tvivo.App.csproj --arch x64 --debug-output`. Arms A and B used the same compiled binary, toggled only by temporary `TVIVO_SKIP_STARTUP_FULLSCREEN=1`; arm C was rebuilt to queue fullscreen after activation. Process samples were taken about every 2 seconds. Run logs and sample CSVs are in `D:\Temp\TvivoCrashAB\`.

| Arm / run | Fatal crash | Window evidence | Process lifetime and triage |
| --- | --- | --- | --- |
| A1: fullscreen before activation | `0xC0000374` | No activation log; no nonzero app window handle sampled | App sampled 11:48:00–11:48:10; gone by 11:48:12; `winapp` triage ended by 11:48:19 |
| A2: fullscreen before activation | `0xC0000374` | No activation log; no nonzero handle sampled | App sampled 11:50:11–11:50:23; no app remained after triage |
| A3: fullscreen before activation | `0xC0000374` | No activation log; no nonzero handle sampled | App caught in one 2-second sample at 11:51:00; no app remained after triage |
| B1: skip fullscreen | No crash | Activation logged; nonzero app window handle in 9 samples, responsive | App sampled 11:51:37–11:51:55; deliberately stopped after 18 seconds; none remained |
| B2: skip fullscreen | No crash | Activation logged; nonzero handle in 9 samples, responsive | App sampled 11:52:34–11:52:52; deliberately stopped after 18 seconds; none remained |
| B3: skip fullscreen | No crash | Activation logged; nonzero handle in 10 samples, responsive | App sampled 11:53:23–11:53:41; deliberately stopped after 18 seconds; none remained |
| C1: fullscreen queued after activation | `0xC0000374` | Activation logged; nonzero handle sampled briefly during failure | App sampled 11:54:42–11:54:44; `WerFault` sampled; none remained after triage |

The window column reports activation and sampled Win32 handles, not a visual screenshot. The B-arm CLI exit code was `-1` because the harness deliberately stopped the healthy app. The six crashing launches returned `-1073740940` (`0xC0000374`). Each crash dump was triaged before the next run, and `Tvivo.App`/`winapp` were absent after the final run. No stream was opened.

All three A dumps have the fatal managed stack `AppWindow.SetPresenter` → `WindowStateController.Apply` (`WindowStateController.cs:39`) → `MainWindow.PrepareForActivation` → `App.OnLaunched`. All three C dumps have `AppWindow.SetPresenter` → `WindowStateController.Apply` → `MainWindow.ApplyStartupFullscreen` → the `DispatcherQueue` callback. Representative full debug logs: `C:\Users\Dell\AppData\Local\Temp\winapp-dumps\debug-73716-20260926-114759.log` (A1) and `C:\Users\Dell\AppData\Local\Temp\winapp-dumps\debug-38396-20260926-115442.log` (C1). The other four crash log paths are in the corresponding `A2`, `A3`, `C2`, and `C3` `winapp.log` files under `D:\Temp\TvivoCrashAB\`.

## EXACT BOUNDARY

Construction and XAML initialization finish in every arm. A fails inside `SetPresenter` before `Activate()`; B reaches `MainWindow activated` and remains responsive until deliberately stopped; C reaches `MainWindow activated`, then fails inside `SetPresenter` from the queued callback. The post-activation callback was reached, as proven by its fatal dump stack, even though its success log did not execute.

## RULED OUT

- The crash is not inevitable from window construction, catalog startup, or the first-chance SQLite exception alone: all three B launches exercised those startup paths and stayed alive without calling `SetPresenter(FullScreen)`.
- Simply moving the same presenter call to the next dispatcher turn after activation is not a stable fix: C crashed 3/3.
- The pre-existing SQLite `0x80073D54` first-chance exception remains the version-matched, caught no-package-identity probe documented in the previous investigation. It is not the fatal `0xC0000374` stack.
- The previous investigation found schema v10 already present and the x64 SQLite native payload present; this A/B did not change either.

## UNCERTAINTY

- `SetPresenter` is the detection boundary, not proof that it made the earlier invalid heap write/free. The same earlier native state may be exposed only by the fullscreen transition.
- The B runs establish startup stability for an 18-second window each, not indefinite stability or correct fullscreen behavior later. C's brief window handles prove a window object existed; the sampler cannot establish what was visibly painted before the crash.
- Process samples are at about 2-second intervals; short-lived app or `WerFault` phases may fall between samples. Crashing app processes persisted for some samples while `winapp`/dump triage ran, but none persisted afterward.
- The source was restored after C without another launch. The current on-disk build output may still contain C until the next build; the source contains the original before-activation call.

## NEXT GATE

The owner approved replacing the fullscreen presenter call. `WindowStateController` now uses Win32 popup style and monitor bounds without any `AppWindow.SetPresenter` transition; see `.codex-handoff-fullscreen.md` for the implementation and clean build evidence. The original A/B results above remain the baseline, not a runtime validation of the replacement. The next gate requires explicit approval to launch the app and validate startup, toggling, cinema, Escape, DPI/multiple monitors, and clean process exit. If heap corruption persists without a presenter transition, preserve a native/full heap-verification dump and isolate the native startup interaction one component at a time. Do not change migration logic or SQLite provider initialization based on the benign first-chance exception.
