# Tvivo Windows spike — Phase B API research

Research-only report; no implementation was created. Sources were checked on **2026-09-17** against current Microsoft Learn pages, Microsoft/Windows App SDK repository material, NuGet metadata, and the VideoLAN LibVLCSharp repository. “Current stable” means the latest non-preview package/release visible in those sources on that date.

## Executive summary

- **WinUI 3/.NET 10 is not currently blocked by an official framework floor.** Microsoft’s current WinUI templates explicitly support `net8.0`, `net9.0`, and `net10.0`; Microsoft Learn describes the supported managed runtime as .NET 8 or later. The current stable Windows App SDK release is **2.4.0**.
- **Native playback has the cleanest XAML integration:** `Windows.Media.Playback.MediaPlayer` + `Microsoft.UI.Xaml.Controls.MediaPlayerElement`, with `MediaSource.CreateFromUri` for a remote Xtream URL. Hardware use is delegated to Windows/Media Foundation and is device/codec dependent.
- **LibVLCSharp WinUI support now exists officially.** Use `LibVLCSharp.WinUI` plus `LibVLCSharp` and the separate native `VideoLAN.LibVLC.Windows` package. The dedicated WinUI package was introduced in 3.10.0; the current stable LibVLCSharp line is 3.10.1.
- **The principal architecture risk is not package availability; it is rendering and lifecycle proof.** A throwaway sample must confirm that the chosen `LibVLCSharp.WinUI.VideoView` behaves correctly in the exact WinUI 3 + .NET 10 packaging mode, and that either engine can expose a sufficiently reliable “first frame” signal for the shared playback abstraction.

## 1. WinUI 3 / Windows App SDK

### Findings

- **KNOWN** — Current stable Windows App SDK release: **2.4.0**, released 2026-08-13. WinUI 3 is included; it is not a separate WinUI 3 runtime package for this app model.
- **KNOWN** — Microsoft’s current Windows app documentation says managed WinUI development supports **.NET 8 or later**. The official Windows App SDK template documentation explicitly lists `net8.0`, `net9.0`, and `net10.0` as supported choices and says current templates default to `net10.0` in the relevant cases.
- **KNOWN** — The 2.x Windows App SDK line is backward compatible to Windows 10 version 1809/build 17763, subject to the release’s support policy and the OS versions Microsoft still services.
- **KNOWN** — The app target must be a Windows TFM, not plain `net10.0`; plan on a form such as `net10.0-windows10.0.26100.0` or the TFM generated by the selected template. The exact target platform version should be chosen during Phase D based on the OS/support matrix.
- **KNOWN** — `Microsoft.WindowsAppSDK` is a native/metapackage-style dependency. The actual runtime deployment choice remains important: packaged, unpackaged framework-dependent, or self-contained have different bootstrap/runtime requirements.

### .NET 10 caveats

- **KNOWN** — There is no Microsoft-documentation blocker saying WinUI 3 only supports .NET 8/9; the current template source explicitly includes .NET 10.
- **ASSUMED** — Existing third-party WinUI controls and native interop code may still carry .NET 8/9 assumptions even though the platform itself supports .NET 10.
- **NEEDS SPIKE** — Restore, build, launch, and publish both a packaged and the intended unpackaged configuration with `net10.0-windows...`, Windows App SDK 2.4.0, and `LibVLCSharp.WinUI` 3.10.1. This environment did not run a build.

## 2. Windows native media playback in WinUI 3

### Recommended API and XAML integration

- **KNOWN** — The current recommended stack is `Windows.Media.Playback.MediaPlayer` with `Microsoft.UI.Xaml.Controls.MediaPlayerElement`.
- **KNOWN** — A `MediaPlayerElement` can be declared in XAML and connected with `mediaPlayerElement.SetMediaPlayer(mediaPlayer)`. Alternatively, assigning a source to the element causes it to create/access an underlying `MediaPlayer`.
- **KNOWN** — For a remote Xtream URL, the relevant source shape is `MediaSource.CreateFromUri(new Uri(url))`, assigned to `MediaPlayer.Source`; `Play()` starts playback unless `AutoPlay` is enabled. `MediaSource.CreateFromUri` does not imply that the server’s container/codec is supported.
- **KNOWN** — The current Microsoft guidance prefers `MediaPlayerElement` over the older `MediaElement` for this API family. Transport controls can be disabled and replaced by Tvivo controls.
- **KNOWN** — `MediaPlayer` also offers `GetSurface`, `SetSurfaceSize`, frame-server mode (`IsVideoFrameServerEnabled`/`VideoFrameAvailable`), playback-session state, buffering, position, duration, and track APIs. Those are alternatives if the default element surface is insufficient.

### Hardware decoding and formats

- **KNOWN** — Decode/rendering is provided by the Windows media stack/Media Foundation and may use hardware acceleration when the OS, driver, device, profile, and stream permit it. The API does not provide a portable “hardware decoding guaranteed” contract.
- **KNOWN** — Microsoft’s codec table lists H.264 decode in MPEG-4, MPEG-2 PS, MPEG-2 TS, AVCHD, ASF, AVI, and MKV-related entries. It lists H.265/HEVC in fMP4, MPEG-4, and MKV-related entries, with an explicit warning that H.265 is not necessarily supported by every device and may require the optional HEVC codec.
- **KNOWN** — MPEG-2/MPEG-1 support can depend on the optional Windows DVD Player codec; HEVC and AV1 can depend on corresponding optional codec packs. This matters for provider streams whose audio/video tracks vary even when the nominal container is `.ts` or `.mkv`.
- **ASSUMED** — HLS may work when the Windows media source accepts the particular HLS manifest/variant and codecs, but the exact behavior for Xtream panel URLs, redirects, MIME types, and unusual transport streams is not established by the generic codec table.
- **NEEDS SPIKE** — Test representative real samples: H.264/AAC MPEG-TS, H.265/AAC MPEG-TS, H.264/AAC MKV, H.265 MKV, and the panel’s HLS form if supplied. Test on the target Windows versions and hardware with and without optional codecs.

### Events, failures, and first frame

- **KNOWN** — `MediaPlayer.MediaOpened` indicates that media opened; `MediaEnded` indicates completion; `MediaFailed` provides `MediaPlayerFailedEventArgs` with `Error`, `ErrorMessage`, and `ExtendedErrorCode`.
- **KNOWN** — For `MediaPlaybackItem`/`MediaPlaybackList`, the item-level failure object is more informative and can expose an error code for network, decoding, or encryption failures where available. For a single `MediaPlayer.Source`, the failure surface is primarily the media error enum/message/HRESULT.
- **KNOWN** — `MediaPlayerElement` has no documented, dedicated `FirstFrameRendered` event in the current API surface.
- **ASSUMED** — `MediaOpened` means the source/streams have opened, not necessarily that a decoded frame has been composited and is visible to the user.
- **NEEDS SPIKE** — Prove the first-frame contract. Candidate approaches are: a conservative “opened + playback state + video dimensions” heuristic; `VideoFrameAvailable` in frame-server mode; or a small custom surface/render observation. Frame-server mode changes responsibility because the app must copy/display frames itself.

## 3. LibVLCSharp and LibVLC on WinUI 3

### Package and integration state

- **KNOWN** — Current stable LibVLCSharp line: **3.10.1**.
- **KNOWN** — The official repository’s 3.10.0 release notes record a breaking packaging change: UWP and WinUI `VideoView` targets moved out of the base package into dedicated `LibVLCSharp.UWP` and `LibVLCSharp.WinUI` packages.
- **KNOWN** — `LibVLCSharp.WinUI` 3.10.1 is the official WinUI view package and contains the WinUI `VideoView` control. This is not merely a community workaround.
- **KNOWN** — `LibVLCSharp` 3.10.1 is the core managed binding. `VideoLAN.LibVLC.Windows` **3.0.23.1** is a separate native-engine package; the WinUI package does not include LibVLC itself.
- **KNOWN** — The official package README requires installing `VideoLAN.LibVLC.Windows` separately. The native package contains the LibVLC binaries/plugins and must be carried into the selected app architecture/package layout.
- **KNOWN** — LibVLCSharp 3.x is the current stable line; LibVLC 4/LibVLCSharp 4 are preview/nightly material and should not be selected for the spike unless the spike is explicitly testing preview APIs.
- **KNOWN** — LibVLCSharp release notes record .NET 10 build support beginning in 3.9.6 and the current 3.10.x line includes modern .NET targets. This is stronger evidence than the older “WinUI is awkward/unsupported” assumption, but it does not prove every WinUI 3 + .NET 10 deployment combination.

### Relevant APIs and state/error reporting

- **KNOWN** — Core types are `LibVLC`, `Media`, and `MediaPlayer`; the WinUI surface is `LibVLCSharp.WinUI.VideoView`.
- **KNOWN** — Playback control includes `MediaPlayer.Play`, `Pause`, `Stop`, `IsPlaying`, `State`, position/time/length properties, and events corresponding to opening, buffering, playing, paused, stopped, end reached, and encountered error.
- **KNOWN** — For direct Win32 rendering, the core binding exposes `MediaPlayer.Hwnd`; the official WinUI package supplies a `VideoView` abstraction intended to manage the WinUI rendering integration.
- **KNOWN** — LibVLC exposes diagnostic logging and `LibVLC.LastLibVLCError`; media parsing also has parse status/events. These are useful diagnostics, but the high-level `EncounteredError` event is not a typed, portable taxonomy equivalent to HTTP/network/codec/decode categories.
- **KNOWN** — The official best-practices documentation says to keep one `LibVLC` instance for the application, explicitly dispose LibVLCSharp objects, and not call back into LibVLCSharp directly from a LibVLC event without switching thread.
- **ASSUMED** — `MediaPlayer.Playing`, `MediaPlayer.State == Playing`, or a video-output (`Vout`) event can be used as a practical “video is progressing” signal, but none is documented as an exact first-composited-frame notification.
- **NEEDS SPIKE** — Confirm that `VideoView` works as a normal child in the intended WinUI 3 XAML tree, including resize, visibility changes, navigation/unload/reload, DPI changes, packaged/unpackaged launch, and x64/ARM64 deployment. Confirm whether the package’s initialization event means “surface ready” or “first decoded frame.”

### .NET 10 and native redistribution caveats

- **KNOWN** — The native package has no managed framework assets; it is a native redistribution dependency, not a replacement for `LibVLCSharp`.
- **KNOWN** — Architecture must match the process/native assets. The release notes call out Windows ARM64 loading/fallback behavior and the dependency on `VideoLAN.LibVLC.Windows 3.0.23.1`; x64 should still be tested independently.
- **ASSUMED** — MSIX/unpackaged deployment details such as plugin discovery, `libvlc.dll` load paths, native DLL search paths, and trimming/single-file settings may require project-specific configuration.
- **NEEDS SPIKE** — Build and run the exact .NET 10 deployment model, then verify that `libvlc.dll`, plugins, and any required runtime assets are found from a clean machine/output directory rather than only from a developer installation.

## 4. Rendering integration inside a WinUI 3 XAML tree

### Options actually available

| Surface | Native engine fit | What is verified | Main caveat |
|---|---|---|---|
| `MediaPlayerElement` | Windows `MediaPlayer` | First-party XAML element; `SetMediaPlayer` is documented | Best default for native playback; not a generic LibVLC host |
| `SwapChainPanel` | Custom Direct3D/video renderer; possible LibVLC custom surface work | `ISwapChainPanelNative.SetSwapChain` and WinUI `SwapChainPanel` are documented; assignment must occur on the UI thread | LibVLCSharp’s official WinUI `VideoView` may hide its own surface strategy; do not assume it is a raw `SwapChainPanel` until inspected/tested |
| Win32 child `HWND` | LibVLC direct `MediaPlayer.Hwnd` | WinUI/Windows App SDK windows are HWND-backed; Win32 interop and native child hosting are documented | A child HWND is an airspace/z-order/input island, not an ordinary composited XAML element; layout, clipping, focus, DPI, and overlay behavior need explicit handling |
| `ContentIsland` / composition surface | Advanced non-XAML rendering | Current Windows App SDK exposes `ContentIsland`, `ChildSiteLink`, and XAML-root integration for Direct3D-backed visuals | Newer/advanced API; does not automatically turn an HWND-based LibVLC output into a composition surface |
| XAML Islands (`DesktopWindowXamlSource`) | Primarily for hosting WinUI in Win32/WPF/WinForms | Official hosting API creates a native child site | This is generally the inverse of Tvivo’s problem if the app is already WinUI 3; it should not be the default playback bridge |

- **KNOWN** — `SwapChainPanel` is a valid WinUI 3 rendering target. The native bridge is `ISwapChainPanelNative.SetSwapChain`, and Microsoft requires that call on the UI thread owning the panel.
- **KNOWN** — WinUI 3 desktop windows are HWND-backed and Microsoft documents retrieving the window handle and performing Win32 interop.
- **KNOWN** — Windows App SDK `ContentIsland` is a current advanced path for hosting non-XAML rendering content, including Composition/Win2D/Direct3D-backed visuals in a WinUI tree.
- **KNOWN** — A true child `HWND` can be hosted/positioned in a Win32 composition/layout arrangement, but normal XAML controls cannot freely paint above it. The app must handle z-order, clipping, hit testing, focus, and resizing.
- **ASSUMED** — The most maintainable shared abstraction is likely two concrete surfaces: native engine owns a `MediaPlayerElement`; LibVLC owns its official `VideoView` if it passes the spike. A forced common `SwapChainPanel`/HWND layer may add complexity without improving interchangeability.
- **NEEDS SPIKE** — Decide whether a single host contract can expose both surfaces without engine-specific layout hacks. Include overlays, full-screen transitions, navigation unload/reload, keyboard/D-pad focus, and resizing in the test matrix.

## 5. Lifecycle and threading

### Native Windows player

- **KNOWN** — WinUI/XAML objects and `SwapChainPanel` interop are UI-thread-affine. Microsoft explicitly requires `SetSwapChain` on the panel’s UI thread.
- **KNOWN** — Many Windows Runtime classes are agile, but UI objects may not be; C#/WinRT documents that callers must respect the threading model of non-agile projected types.
- **KNOWN** — `MediaPlayer.Close` disposes associated resources; in C# this is exposed through `IDisposable`/`Dispose`.
- **ASSUMED** — Create/connect the `MediaPlayerElement` and its player on the WinUI UI thread, marshal UI/state changes back through the window’s `DispatcherQueue`, and perform shutdown while the visual tree is still valid.
- **NEEDS SPIKE** — Confirm whether source assignment, stop, and disposal can safely be awaited/called from a background service or must all be serialized through the UI dispatcher in the chosen wrapper.

### LibVLCSharp

- **KNOWN** — LibVLC creates native worker threads; event callbacks may arrive off the UI thread. VideoLAN explicitly warns not to call back into LibVLCSharp from a LibVLC event without switching thread.
- **KNOWN** — LibVLCSharp objects are `IDisposable`; explicit disposal is required. VideoLAN recommends one `LibVLC` instance for the application and multiple `MediaPlayer` instances as needed.
- **KNOWN** — `MediaPlayer.Stop()` is synchronous and joins VLC threads; the source documentation warns it can deadlock if called from a VLC callback. Stop/dispose must therefore be coordinated outside callback execution.
- **ASSUMED** — UI-only operations on `VideoView`/its visual surface should be performed on the WinUI UI thread, while playback commands can be serialized through a dedicated player coordinator if the binding permits them.
- **NEEDS SPIKE** — Validate the exact disposal order: detach/unload `VideoView`, stop `MediaPlayer`, unsubscribe events, dispose `Media`, dispose `MediaPlayer`, then dispose the singleton `LibVLC` only at app shutdown. Validate navigation-away during opening/buffering and during a callback.

## 6. Error/event reporting fidelity

### Comparison

| Category | Windows `MediaPlayer` | LibVLCSharp/LibVLC |
|---|---|---|
| Open/source failure | `MediaFailed` with `MediaPlayerError`, message, extended HRESULT; item/list APIs can expose richer error code | `EncounteredError`, state/events, `MediaPlayer`/`Media` state, `LibVLC.LastLibVLCError`, and native diagnostic logs |
| Network failure | Often represented by a media error/HRESULT/message; item-level docs explicitly include network errors where possible | Usually an opaque encountered-error/state plus native log text; HTTP details may be available only through logs or lower-level access |
| Unsupported container/codec | Can often be inferred from `MediaPlayerError`/HRESULT/message, but no promise that every failure maps cleanly to “unsupported codec” | LibVLC’s broad demux/codec stack may open more inputs, but high-level managed event does not guarantee a typed codec-vs-demux-vs-network category |
| Decode failure after open | May arrive later as failure or stalled/buffering behavior; must observe playback session/state as well | May be an error event, stopped state, or logs; exact distinction is engine/log dependent |
| Authentication/HTTP status | Not a documented, stable high-level status API for this use case | Not a stable high-level typed status API for this use case |
| First frame | No documented direct event on `MediaPlayerElement`; `MediaOpened` is insufficient proof | No documented exact first-composited-frame event in the common API; `Playing`/Vout/surface events are proxies |

- **KNOWN** — The native player has the more structured public failure object: `Error`, `ErrorMessage`, and `ExtendedErrorCode`; `MediaPlaybackItemFailedEventArgs.Error` can enumerate network, decoding, or encryption causes when possible.
- **KNOWN** — LibVLCSharp exposes a broad event/state surface and native error/log facilities, but the documented high-level API does not promise a stable typed taxonomy for network failure, unsupported codec, and decode failure.
- **ASSUMED** — A provider-facing abstraction should normalize failures into coarse categories such as `OpenFailed`, `NetworkOrAuth`, `UnsupportedOrUndecodable`, `Stopped`, and `Unknown`, while retaining engine-specific raw details for diagnostics.
- **NEEDS SPIKE** — Feed intentionally bad URLs, refused connections, HTTP auth failures, valid-but-unsupported codecs, truncated streams, and a stream that opens but fails during decode into both engines. Record event order, thread, error code/message, and whether the UI can distinguish the categories without parsing localized text.

## Recommended Phase D spike acceptance criteria

1. `net10.0-windows...` WinUI 3 app builds and launches with Windows App SDK 2.4.0 in the selected packaging mode.
2. Native engine displays representative remote MPEG-TS/MKV/HLS samples through `MediaPlayerElement`; record hardware/codec behavior and failure events.
3. LibVLCSharp 3.10.1 + `LibVLCSharp.WinUI` 3.10.1 + `VideoLAN.LibVLC.Windows` 3.0.23.1 displays the same samples from a clean output directory.
4. Both engines survive source replacement, stop, navigation unload/reload, resize/DPI changes, and app shutdown without native crashes or leaked callbacks.
5. A shared playback state model can report opening, buffering, playing, paused, ended, failed, and first-visible-frame with documented confidence/limitations.
6. Error tests record whether network/auth, unsupported codec/container, and decode failure can be distinguished without relying solely on free-form localized strings.

## Bottom line

The Windows spike is technically viable on .NET 10 with current stable WinUI 3/Windows App SDK tooling. The old concern that LibVLCSharp has no WinUI integration is no longer accurate: the official `LibVLCSharp.WinUI` package exists and is current. The architecture should nevertheless remain provisional until Phase D proves the WinUI `VideoView` surface, native asset deployment, disposal/thread behavior, and a first-frame/error contract against real Xtream-style streams.
