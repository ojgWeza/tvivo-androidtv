# Tvivo Windows Rewrite Spike — Phase A Repository Archaeology

Date: 2026-09-17  
Scope: static inspection of the existing checkout at `D:\HCode\Tvivo`  
Status: inspection only; no existing source, build file, test, fixture, or project was modified.

## Executive summary

Tvivo is currently a Kotlin/Gradle repository with three modules:

| Module | Platform | Current role |
|---|---|---|
| `app` | Android TV, Kotlin/JVM/Compose | Main Android product slice; Retrofit/OkHttp Xtream client, Room cache, DataStore/Tink credentials, Media3 playback |
| `desktop` | Windows JVM, Kotlin Compose Desktop | Existing Windows desktop product slice; Java `HttpClient`, Gson, raw SQLite, Windows DPAPI, bundled libmpv through JNA |
| `shared-core` | Kotlin/JVM | Small shared layer containing credentials/address parsing, account identity, and Xtream stream URL construction |

There is no `.sln`, `.csproj`, WinUI, WPF, WinForms, MAUI, Avalonia, or C# code in the repository. The existing Windows implementation is evidence for the future rewrite, not a .NET foundation. The Android implementation contains the more defensive Xtream parsing and catalog-sync rules; the desktop implementation contains the more directly relevant Windows persistence, DPAPI, native-window, and player-lifecycle evidence.

The best Phase B inputs are therefore behavior contracts and fixtures, not wholesale code reuse. The provider URL rules, account scoping, JSON edge-case handling, zero-row protection, real migrations, and playback lifecycle lessons should be ported conceptually/mechanically. The Android Room schema and desktop SQLite schema are related but not identical and should not be treated as a drop-in database migration for the new Windows spike.

Important areas:

- `desktop/src/main/kotlin/com/dev/tvivo/desktop/Main.kt`: Windows Compose application entry/state gate.
- `DesktopShell.kt`: route state, browse/detail/player screens, native surface integration, input forwarding, watchdog and lifecycle wiring.

The desktop app is not a provider-neutral architecture: Xtream action names and response fields are parsed inside the catalog repository, and `DesktopShell` constructs/owns `MpvPlayer` directly. There is no provider interface and no playback-engine interface.

### Shared module

`shared-core/src/main/kotlin/com/dev/Tvivo/` contains:

- `auth/Credentials.kt`: server address parsing, scheme/port/IPv6 normalization, API base URL.
- `auth/AccountIdentity.kt`: truncated SHA-256 identity from normalized host/port/username.
- `data/StreamUrlBuilder.kt`: live/movie/episode URL construction and redaction.
- `data/AppError.kt`: shared error taxonomy.

This is the only meaningful code sharing between Android and desktop. Android and desktop retain separate HTTP clients, parsers, repositories, stores, UIs, databases, and playback implementations.

### Existing Windows work and absent work

Existing Windows work is Kotlin Compose Desktop, not .NET. Active playback is bundled libmpv embedded in an AWT `Canvas`/HWND using `wid`; mpv's OSC supplies controls. There are test-only two-window/overlay and render-API experiments, but the audit marks the render API as not accepted. Historical LibVLC/vlcj implementation attempts are documented and no active LibVLC dependency or production LibVLC source remains.

No existing Windows rewrite solution, C# project, WinUI project, or new sibling spike directory exists in the inspected inventory.

## 3. Xtream behavior worth porting

The following should become explicit contracts in the new C# core/client and should be tested before UI work:

1. **Authentication semantics:** evaluate both HTTP status and the JSON body. A wrong password can be HTTP 200 with `user_info.auth = 0`; `status` must be Active. Read `server_info.port`, `https_port`, and `max_connections` as panel/account data.
2. **Endpoint/action mapping:** use the exact action names. Series is `get_series`, not `get_series_streams`. `get_vod_info` is the observed source of movie plot/description; list VOD rows do not reliably contain plot.
3. **Full-catalog behavior:** on the observed panel, omitting `category_id` returns all VOD, live, and series rows in one response. This enables a full-catalog sync tier, but it is not a universal Xtream guarantee. A rejecting panel may return an object rather than an array; treat zero rows/object/rejected/truncated responses as non-authoritative and preserve the previous catalog.
4. **Streaming parse:** large list responses must be parsed incrementally and written in chunks. Android uses `JsonReader` and chunked transactions because the VOD response is approximately 15 MB and materializing it is too expensive for the target TV memory budget. Desktop currently materializes full Gson arrays; that is a known limitation, not a model to copy.
5. **Field differences:** live uses `stream_id`, `stream_icon`, and `ext`; VOD uses `stream_id`, `stream_icon`, and `container_extension`; series uses `series_id`, `cover`, and `last_modified`; `category_id` can be numeric for series and string for other types.
6. **Series shape:** `episodes` is an object keyed by season number strings. Keys can be non-contiguous; season `0` is valid; the key is authoritative when the episode body disagrees. Episode `id` is a string and must remain a string in storage and URL construction.
7. **Duration:** prefer the human-readable `duration` clock field; observed `duration_secs` values are wrong (single/double-digit seconds for long episodes). Keep `duration_secs` as fallback only.
8. **Empty series responses:** an empty or malformed `get_series_info` must not delete an already cached season. The Android repository deliberately refuses to replace a non-empty cache with zero parsed episodes.
9. **URLs:** `direct_source` is typically empty; construct URLs from IDs and extensions. Live uses `ext`, movie/episode use `container_extension`; default extension fallback is needed. Encode username/password path segments and redact them before diagnostics.
10. **Transport:** panels commonly use HTTP on non-standard ports, so cleartext permission is deliberate in Android. The new Windows client should retain normal certificate validation, investigate HTTPS fallback using `https_port`, and never add trust-all certificate behavior.
11. **Text/data quality:** titles may be Arabic or mixed RTL/LTR and quality tokens may duplicate the title. The Android `NameNormalizer` strips quality/empty bracket artifacts while retaining raw and display forms. Categories must not be truncated to one line because visually identical truncation can create false duplicate categories.
12. **Account scoping:** catalog, artwork references, favorites, resume positions, sync metadata, and episode rows must be scoped by stable account identity. A new account must not expose another account's cache.

## 4. Security and account behavior

### Current Android behavior

`CredentialsStore.kt` stores a Gson JSON record containing host, optional port, username, password, and HTTPS choice as an opaque Base64 blob in Jetpack DataStore. The plaintext JSON is encrypted with Tink AES-256-GCM under an Android Keystore master key. Reads, writes, and keyset creation run on `Dispatchers.IO`. If the key is invalidated or decryption/decoding fails, the store wipes the blob and keyset and returns null so the UI re-prompts rather than crash-looping. The project explicitly rejects `EncryptedSharedPreferences` and clearing app data because the non-exportable keyset makes recovery unsafe.

### Current Windows behavior

`WindowsCredentialsStore.kt` writes `%APPDATA%\Tvivo\credentials.dat`. It serializes the shared `Credentials` object to Gson JSON, protects the UTF-8 bytes with Windows current-user DPAPI via `Crypt32Util.cryptProtectData`, Base64-encodes the ciphertext, and writes ASCII text. Load Base64-decodes and calls `cryptUnprotectData`; any exception produces null. Save creates the parent directory; wipe deletes the file. The desktop login stores the corrected port returned by `server_info` when the user supplied only a host.

### Rewrite implications

DPAPI is the natural Windows equivalent to the current desktop behavior and is a candidate for a carefully tested .NET port. The spike must still decide and test: `DataProtectionScope.CurrentUser` versus machine scope; file ACLs; atomic replacement; format versioning; corruption/key failure recovery; roaming/backup behavior; logout semantics; whether server/username should be separately indexed; and redaction of URLs/exceptions/native logs. The future app must preserve the rule that a failed decrypt returns to login without silently exposing or deleting unrelated user data. Account identity should remain independent of the password, as in the current code, unless the product explicitly changes account-switch semantics.

## 6. Playback lessons already learned

### Native surface and controls

The active desktop player embeds libmpv in an AWT `Canvas` using a Windows HWND (`wid`). The canvas is a heavyweight native surface. Compose controls placed casually over it can become invisible or unclickable depending on Windows z-order. The current design either keeps mpv's OSC controls in the native surface or uses deliberate separate window/layout boundaries. `docs/design/desktop-player.md` explicitly calls for opaque sibling bands or a two-state layout, not an unreliable translucent overlay.

### Threading and teardown

Historical LibVLC/vlcj work encountered races around release, resume seek, state reads, close, and late play. The current libmpv implementation serializes every native call—including create, initialize, commands, event drain, and terminate—on a dedicated owner thread. `close()` uses a terminal marker and bounded wait. `MpvPlayerCloseTest.kt` protects the most important teardown guarantees.

### Stale callbacks and channel switching

The current mpv player uses a generation counter and drops state/position callbacks from an older attempt after a newer attempt or terminal state. This is the repository's explicit defense against stale channel/media events updating the current screen. Any dual-engine C# abstraction must retain an attempt/session generation or cancellation token that is checked at every callback boundary; cancellation of a task alone is not enough to stop late native events.

### Input routing and focus

The embedded mpv child is disabled for direct OS input, so `DesktopShell.kt` forwards AWT mouse, motion, wheel, keyboard, focus, and resize events through mpv commands. Mouse movement is coalesced; coordinates are scaled to mpv OSD dimensions; held keys are released on focus loss/disposal. `docs/learnings.md` records that stale click coordinates and held keys on disposal were real bugs caught during review. The future WinUI player should treat native input ownership and focus transitions as explicit state, not incidental control behavior.

### Watchdogs and progress

The desktop watchdog requires two strictly increasing position samples and stops an active, non-paused attempt after 20 seconds without genuine progress. Android has separate first-frame and buffering watchdogs in `PlayerActivity.kt`. These are useful safety contracts, but timeout values should be revalidated per engine and network mode; they are not proof of successful playback.

### LibVLC history

`IPTV_ARCHITECTURE_AUDIT.md` and `docs/decisions.md` record that the LibVLC path reached opening/playing and then stalled in buffering under real provider playback despite cache/options tuning. The initial concurrency implementation had multiple races. A hand-built Compose transport-control layer was rejected as an ongoing maintenance burden. These facts justify a LibVLCSharp gate in the rewrite, but do not prove that LibVLCSharp will fail or succeed; the new spike must test it independently with local MP4/MKV/TS and provider-like HTTP behavior.

### Render API and dual-engine boundary

The libmpv render API/Skiko experiment failed at `mpv_render_context_create` with `-18` (`not supported`) and a native OpenGL initialization complaint, while production remained on HWND embedding. This is a hard piece of evidence against assuming a Compose-compatible render surface. The new WinUI spike should test native Windows playback and LibVLCSharp behind a narrow engine contract, with surface ownership and cancellation documented before adding shared controls.

### Stream scope

Current playback is direct `.mp4`, `.mkv`, and `.ts`; no HLS, UDP, RTSP, retry/reconnect, failover, custom headers, cookies, proxy, catch-up, recording, EPG, or explicit hardware-decoding policy is implemented. Live `.ts` and series `/series/` provider playback have not been automated-executed because the observed account has `max_connections = 1`.

## 7. Risks and unknowns

1. **No current .NET baseline:** WinUI 3/.NET 10 packaging, WebView/native surface decisions, trimming, single-file/native DLL deployment, and C# interop have no repository evidence.
2. **Native engine compatibility:** Windows native playback API choice and LibVLCSharp version/runtime packaging are not evaluated here. Existing mpv evidence is not a substitute.
3. **Provider variance:** full-catalog omission, quoted/numeric fields, HTTPS fallback, auth response details, malformed empty responses, and extension defaults vary among Xtream panels.
4. **Credential URL exposure:** Xtream puts credentials in API query strings and playback paths. Redaction must cover .NET exceptions, `HttpClient` logging, WinUI diagnostics, native engine logs, crash reports, and process-visible command lines.
5. **DPAPI recovery and portability:** current-user protection may intentionally make credentials unavailable under another account or after profile changes. Current code has no dedicated test or versioned file format.
6. **Storage divergence:** Android Room v5 and desktop SQLite v8 have different schemas and semantics. A new Windows database should be designed from the behavior contract, with migration tests, rather than copied as if compatible.
7. **Catalog memory pressure:** desktop materializes full JSON/catalog lists and artwork bytes; Android's chunked parser/generation strategy is safer for large panels.
8. **Cancellation races:** native callbacks can arrive after cancellation, close, or media replacement. Generation filtering and owner-thread serialization are mandatory design inputs.
9. **Surface/input layering:** WinUI composition and native playback window ownership may reproduce or change the AWT heavyweight-surface problem. A dual-engine abstraction must not hide surface lifecycle requirements.
10. **Unverified playback:** current audit evidence supports local fixture and historical testing, but current real-provider libmpv success is not independently proven in this inspection. No live or episode stream was opened.
11. **Missing direct credential tests:** Android Tink/DataStore and desktop DPAPI behavior have no obvious dedicated unit test in the inspected test inventory; this is a gap to close in the spike.
12. **No provider abstraction:** Xtream concepts leak through current repositories and models. A future provider-neutral core will need explicit normalized domain types and an Xtream adapter boundary.
13. **Documentation drift:** the supplied project instructions refer to `todo-tree\00-overview.md` and `bible-detail\claude-07-agent-division.md`, but those paths are absent in this checkout. The current `PROJECT-BIBLE.md` consolidates the project rules and `TODO.md` is the live work queue; this discrepancy should be resolved before a larger migration relies on path-based process automation.
