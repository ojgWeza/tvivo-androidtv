# Android Network Diagnostics — implementation plan

**Scope:** A separate Settings → **Network diagnostics** page for TV, phone and tablet. It explains the active route, recent failures, and the cheapest useful next step. Opening the page makes no network requests. Only **Run check** starts probes. No automated test opens a provider stream; no provider URL, host, username, password, token, title, or full IP enters the UI, log, clipboard, or default export.

## Fit with the current app

`SettingsScreen` already links to the general `DiagnosticsScreen` through `MainActivity.Route.Diagnostics`; add a sibling route and row, preserving the existing page. `DiagnosticLog` already persists 200 entries and offers `export(context, appendix)`, but its freeform `redact` misses bare hostnames/IPs and export does not scrub stored entries or the appendix again. Treat structured, allowlisted fields plus export-time scrubbing as a release gate. `PlaybackService` owns retry/stall decisions and HTTP source errors; `SingleStreamConnectionGate` and `PlaybackHandoff` protect stream opens. Catalog errors originate in `CatalogSyncer` and repositories; `ErrorMapper` currently collapses some causes, so capture typed events **before** mapping. `ACCESS_NETWORK_STATE` and `INTERNET` are already declared; target SDK is 34, minimum 24.

## Passive snapshot and permissions

Use `ConnectivityManager.activeNetwork`, `NetworkCapabilities`, `LinkProperties`, and a lifecycle-scoped default-network callback. Capture transport (Ethernet/Wi-Fi/cellular/VPN/other), validation/captive flags, metered state, `getRestrictBackgroundStatus`, proxy **presence**, Private DNS **off/automatic/strict presence**, DNS server count and address-family availability. Never retain or display DNS/proxy addresses, SSID/BSSID, gateway, interface name, local/provider IP, or Private DNS hostname. Mark a VPN's underlying transport unknown unless Android actually reports it. Snapshot changes create small, debounced connectivity events, not continuous polling. `VALIDATED` means Android's last check succeeded, not that the panel or a stream works; absent validation is inconclusive.

On Wi-Fi, try `NetworkCapabilities.transportInfo as? WifiInfo` for RSSI, receive link speed and frequency; derive 2.4/5/6 GHz from frequency, show unknown for unavailable/sentinel values. `WifiManager.getConnectionInfo()` is deprecated on Android 12; use only a guarded older-device fallback if necessary. `ACCESS_WIFI_STATE` is a normal permission if required for that fallback. Connected Wi-Fi details are device/API dependent and can require **dangerous** `ACCESS_FINE_LOCATION`, Location enabled, and Android 12's location-info callback flag. Default v1: **do not add/request location**; show “Wi-Fi details unavailable on this device” and keep the rest useful. If a later opt-in precision mode is approved, explain the permission on TV/phone, request only while foregrounded, handle denial, and never collect SSID/BSSID. No `CHANGE_WIFI_STATE`, location scan, ICMP/root permission, or settings mutation.

## User-started check

One structured coroutine job, quick checks within about 15 seconds plus an optional ≤8-second download (overall cap 25 seconds); per-step deadline, cancel on Back, route change, network handoff, or another tap. Bind probes to the snapshot's `Network` so a handoff cannot mix results. Close every response/socket in `finally`; at most **one provider request at a time**. A shared probe-admission check must skip the provider step during playback or an active catalog sync and recheck immediately before dispatch. Show `pending/running/pass/fail/skipped` and elapsed time per step. Do not retry 403/429 automatically or follow a redirect to an unknown host. Use two reviewed, replaceable **neutral HTTPS endpoints** with no account data: a 204 endpoint and a bounded-download endpoint; document the contacted services and approximate data use before the tap. No background schedule or analytics.

| Step | Measurement and bounds | Honest result / skip |
|---|---|---|
| DNS | Time a system resolve through `Network.getAllByName` for the neutral host and the account host; compare the same neutral name with one public DNS-over-HTTPS resolver, sequentially, each ≤2 s. Discard answers. | Public resolver comparison is disclosed and skipped if strict Private DNS is set or policy blocks it. A discrepancy suggests DNS trouble; caches, VPNs, and geo answers can differ normally. |
| Internet / captive | HTTPS 204-style GET, ≤2 s and negligible body; check Android validated/captive flags and redirect/HTML instead of 204. | A blocked test host alone does not prove Internet failure. Offer Wi-Fi sign-in/settings if portal evidence agrees. |
| Provider / TLS / clock | One tiny `player_api.php` authenticate call through the existing credential/client path with probe-specific ≤3 s timeout, only when no playback/catalog call is active; read status and bounded body. For HTTPS, preserve normal certificate validation. Compare device clock with a neutral HTTPS `Date` header when available; classify certificate validity-time errors separately if TLS fails before a header arrives. | A panel 200/auth response proves its control path, not streaming. HTTP panels have no provider TLS test. A Date header is approximate; show clock suspicion for a large offset or certificate time error, with the evidence named. Never disable cert checks. |
| Delay / instability | 4–5 sequential small HTTPS requests to the neutral endpoint; record median and spread of round-trip times (jitter proxy) plus failure count. | Label failures “sample requests failed”; this is **not IP packet loss**, ICMP ping, or a line-quality guarantee. True packet-loss sampling needs a controlled echo endpoint and can be confused by UDP filtering; never fabricate a loss percentage from HTTP. |
| IPv6 | Where both families are available, compare bounded A and AAAA resolution and separate HTTPS connection attempts to a dual-stack neutral host, preserving hostname/SNI; ≤2 s per family. | Diagnose “IPv6 path may be broken” only if IPv4 succeeds and IPv6 repeatedly fails. Skip for IPv4-only networks/hosts. |
| Throughput | Single neutral HTTPS download, stop at **3 MiB or 8 s**, whichever first; measure payload bytes/time after connection, then close. Compare measured Mbps with **1.5 × known selected-track bitrate** when Media3 reports a credible value. | Skip on metered/restricted data or while playing; offer a separately confirmed data-use option on metered connections. If bitrate is unavailable, say “speed measured; stream requirement unknown.” Never infer stream bitrate from Wi-Fi link speed, resolution alone, or `duration_secs`. |

While anything is playing (including background audio/PiP), skip the provider call and throughput/latency probes that could disturb playback; show why and retain passive/recent-event findings. Recheck the player-service state immediately before every provider probe, then cancel if playback starts. Never call a media URL, open a stream, or use the provider for a speed test. A fast neutral host plus bad provider outcomes supports “provider path or provider may be slow/limiting”; it cannot distinguish ISP throttling from provider overload, peering, VPN, or account limits. Suggest a same-content comparison on another network only as a manual next step.

## Recent problems and diagnosis engine

Create a separate app-private, bounded **typed** ring (e.g. last 100 network events or 7 days, whichever smaller) with timestamp, current-account partition key kept local, source (`playback/catalog/connectivity/check`), event kind, HTTP status bucket/code, phase, and optional bounded duration/count. No exception messages, URLs, raw addresses, titles, or credential-derived text. Record 403, 429, 5xx, DNS failures, connect/read timeouts, TLS failures, stalls, retries, handoff cooldown/recent-close 403, network loss/change, and probe outcomes. Persist atomically in order; restore after process death. Group in the UI by kind with count and first/last local times, sorted newest first. Do not mix an old account's evidence with the current one. Keep `DiagnosticLog`'s general log and `CrashDiagnostics` separate; add only safe summary events there. Re-scrub old persisted entries and the report appendix at export, with privacy tests including raw/encoded credentials, bare hosts, IPv4/IPv6 literals, redirects, and exception text. Default export contains **no** provider host; any future explicit host-included export needs a separate owner decision and clear on-device confirmation.

Put `NetworkSnapshot + ProbeResults + RecentEventSummary → List<Finding>` in pure `shared-core`, no Android types, clock or network access. Findings contain stable ID, severity (`critical/warning/info`), plain-language title, quantified evidence/time window, ordered step IDs and a confidence/limitation sentence. The app localizes step IDs and values. Highest-severity, strongest-evidence findings first; deduplicate related symptoms (e.g. captive portal ahead of DNS failures). “Your connection looks OK in these checks” appears only when mandatory checks passed, no important recent failures exist, and no relevant step was skipped; otherwise say what was not checked. Thresholds below are starting heuristics, covered by boundary tests and revised with device evidence.

| Evidence → finding | Recommended steps, cheapest first |
|---|---|
| No active route / repeated disconnects | Check TV network settings/cable; reconnect Wi-Fi; restart router if other devices also fail. |
| Captive flag plus redirect/non-204 | Complete Wi-Fi sign-in in Android network settings; retry check. |
| Wi-Fi RSSI below −70 dBm or low/unstable receive link rate | Move TV/router or remove obstruction; try 5 GHz if in range; use Ethernet. Signal/link rate alone do not prove Internet speed. |
| Connected at 2.4 GHz with poor speed/instability | Try the router's 5 GHz network near the TV; if distance is large, compare Ethernet. 2.4 GHz alone is informational. |
| System DNS slow (>500 ms median) or fails while public DoH succeeds | Temporarily set Private DNS to Automatic if configured; restart router; consider router DNS change. Different resolver answers alone are not a failure. |
| IPv6 attempts fail twice while IPv4 succeeds | Restart router; update router firmware/settings; ask ISP about IPv6; use IPv4 as a temporary comparison. |
| Neutral HTTPS `Date` offset >5 min **or** a certificate validity-time error | Turn on automatic date/time and time zone in Android settings; retry. Say which signal was observed. Other TLS failures: check VPN/proxy or contact server owner; never bypass validation. |
| Neutral median latency >150 ms, spread >100 ms, or ≥2/5 failed samples | Pause other downloads; try Ethernet/closer Wi-Fi; compare another network. Report HTTP sample failures, not packet-loss %. |
| Throughput <1.5 × **known** stream bitrate | Try a lower-bitrate source/quality if the provider offers one; stop other downloads; try Ethernet. Neutral throughput does not guarantee provider throughput. |
| Provider control call fails but neutral checks pass, or repeated provider 5xx/timeouts | Retry later; compare another network; contact provider with redacted status/time. Label ISP/provider throttling only “possible,” never a proven cause. |
| Repeated stream 403 with reported `max_connections`/recent handoff context | Stop playback on another device if applicable; wait about 60 s for the old connection to clear; retry once. A 403 may also mean auth/policy and is not proof of a second connection. |
| 429 (catalog or playback) | Wait the indicated `Retry-After` when present, otherwise a short pause; avoid repeated refresh; contact provider if persistent. |
| VPN/proxy/strict Private DNS present **and** failures | Temporarily turn it off for a comparison, then restore it; do not claim it caused the failure from presence alone. |
| Metered + restricted background/data saver | Allow Tvivo background data in Android settings if background playback/sync fails; use unmetered Wi-Fi for checks. Do not suggest disabling data saver globally first. |
| Recent stalls/retries or handoff cooldown without matching probe failure | Retry once after a short wait; if recurring, compare wired/another network and share redacted report. A stream-level stall may be media/decoder related. |

## Screen contract

Settings gets a distinct **Network diagnostics** row. TV opens with focus on one prominent **Run check** button; Back returns to Settings and restores row focus. A top summary reports the strongest finding and exact check age. Under it: connection facts (unknowns explicit), per-test progress, ordered expandable findings (evidence visible, numbered fixes), and **Recent problems** counts/timestamps. Secondary **Copy report** and **Export report** actions use one redacted report renderer; export calls `DiagnosticLog.export(context, sanitizedAppendix)` and the chooser, copy uses clipboard with a confirmation. Never display the raw host or IP. Show “No recent problems recorded” separately from “No network problem found.”

Use `LocalIsTelevision`, adaptive spacing, theme color roles and `TvType`, 48 dp or larger targets, large wrapping text, clear focus frame, logical D-pad order, scroll-to-focused expanded step, and readable contrast in light/dark. Phone/tablet use the same content with touch and safe insets. No keyboard. Add stable tags: `networkDiagnosticsEntry`, `networkRunCheck`, `networkCancelCheck`, `networkSummary`, `networkTest_<id>`, `networkFinding_<id>`, `networkRecentProblems`, `networkCopyReport`, `networkExportReport`. Add English and Arabic resources in `values/strings.xml` and `values-ar/strings.xml` for all titles, status/skip reasons, units, evidence templates, steps, clipboard confirmation and accessibility descriptions; verify RTL focus/read order and Arabic numeral/plural formatting.

Each slice must build on its predecessor and pass `:shared-core:test :app:testDebugUnitTest :app:assembleDebug` before the next. Device install/emulator launch needs separate owner approval; the final device run is a combined batch, not one install per slice. Risks to check: OEM Wi-Fi redaction, VPN route attribution, captive-probe false positives, public endpoint availability/privacy, Android cancellation of blocking DNS, clock-header precision, transfer cap enforcement, and producer/write ordering. No Room migration, no new analytics SDK, no stream requests from the check.

## Owner decisions before probe implementation

1. Which neutral HTTPS services may receive a user-started check (DNS comparison, 204 and ≤3 MiB download)? Proposed default: select two documented, replaceable public services after endpoint/terms review and disclose them beside Run check; if third-party contact is unacceptable, ship passive + provider-only checks and mark neutral tests unavailable.
2. Keep precise Wi-Fi signal/band **best effort without location permission** for 1.0 (recommended), or add an explicitly opt-in location-permission flow for devices that hide these fields?
3. Is an honest HTTP request-failure sample enough for 1.0, or is a controlled echo endpoint required for an actual packet-loss estimate? Recommendation: ship the request-failure sample first; avoid an unverified “packet loss” claim.
