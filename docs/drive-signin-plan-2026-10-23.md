# Google Drive library source — Android plan — 2026-10-23

**Status:** plan only; no code, build, Drive account, or emulator work is authorized by this document. Scope is Android phone, tablet, and TV first. OneDrive and WinUI are later adapters to the same index format. The owner has decided that Drive stores **small indexes of external media links**, never the media itself. The initial Drive library contains about five movies, two short series, and five songs; its uploaded data should total only a few kilobytes.

## 1. Current seams and architecture decision

- `MainActivity` routes carry `Credentials`, startup calls `CredentialsStore.load()`, `BrowseViewModel` constructs `VodRepository` / `SeriesRepository` / `LiveRepository` from those credentials, and `playItem` builds Xtream URLs. There is no general provider abstraction today. Introduce `SourceSession` (`Xtream` or `Drive`) and a source factory above these paths; adapt Xtream unchanged. `DriveSource` owns authorization, folder discovery, index reads, and sync. A later `OneDriveSource` implements the same `IndexStore` (`listChildren`, `createFolder`, `readIndex`, `writeIndex`, `metadata`) and feeds the same parser. Keep provider-specific API clients below this boundary.
- Keep one **active source** at a time initially, but make the encrypted source store capable of holding multiple saved sources, consistent with the product bible's two-free-sources promise. Switching is staged: authenticate and validate the candidate first, then atomically change the active source; Back or failed consent returns to the prior source. Never call `CredentialsStore.wipe()` while switching. Migrate the current single Xtream credential blob without clearing app data or regenerating the Tink keyset.
- Reuse `categories`, `favourites`, `resume_positions`, `watched`, `recently_played`, `catalog_sync`, image cache, search and home policies through a **source-scoped account key**. Use `drive:` plus a hash of Drive `about.get`'s `user.permissionId`; never use an email address as a database key. Keep existing `vod` / `series` content-type keys within that distinct account. Drive has no Live list. Add `music` as a content type; songs can have favourites and recent plays, while Continue Listening uses the existing resume policy where duration is known. Make search and My Tvivo query the active source and include Music where relevant.
- Use **new Drive movie, show, and episode tables** and DAOs, plus `music_tracks`, instead of coercing UUIDs and direct URLs into Xtream's integer `streamId` / `seriesId` tables. Existing Xtream entities and `StreamUrlBuilder` remain Xtream-only. Drive movie and episode IDs are stable strings; rows carry the validated direct URL, display/normalized name, category, poster, year, plot, and generation. Series show rows own seasons and episodes from the index, not `get_series_info`. A Drive repository adapts these rows into the existing `BrowseItem`, detail, paging/search, shelf, and playback contracts. Never overwrite a Drive row with an Xtream parser response.
- **Room v8** is required from the current v7 development schema: add Drive movie/show/episode tables, `music_tracks`, and a `drive_index_state` table with file IDs, version fingerprints, last successful sync and bootstrap state; extend any active-source dispatch metadata as needed. Preserve v3→v4→v5→v6→v7 migrations and add `MIGRATION_7_8`; export `8.json`. Test upgrades from real v5, v6, v7 schemas and preservation of favourites, resume, profiles and watched rows. Never use destructive migration. Treat `PROJECT-BIBLE.md`'s v7 as current; `PRODUCT-BIBLE.md`'s v5 note is stale.
- Put the **versioned JSON parser, URL and ID validation, and normalized source models in `shared-core`** so Android and later WinUI can share golden JSON vectors. Room, Google auth and Drive REST clients stay Android-specific. Folder bytes are plain UTF-8 JSON, with no Kotlin or Android serialized types.

## 2. Folder and index contract

Visible My Drive hierarchy (folder MIME `application/vnd.google-apps.folder`; index MIME `application/json`):

```text
Tvivo Library/
  library.json                 # schema/seed completion marker, not a media list
  Movies/index.json            # movie links
  Series/index.json            # shows, seasons, episode links
  Music/index.json             # song links
```

`library.json` is `{ "format": "tvivo.link-library", "version": 1, "bootstrap": "complete" }`. Each list is an object with `format`, `version: 1`, `kind` (`movies`, `series`, `music`), and `items`. Strings and IDs are UTF-8; IDs are user-stable UUID strings that survive title edits; array order is display order. Unknown optional fields may be ignored; unknown major version, duplicate IDs, wrong `kind`, missing required data, and malformed JSON reject **that whole file** without replacing its last good local generation. Example (illustrative URLs, never the shipped seed):

```json
{
  "format": "tvivo.link-library", "version": 1, "kind": "series",
  "items": [{
    "id": "d44bfc8e-4106-4a8a-8b69-b57c1d03486a",
    "title": "Example Series", "group": "Classics", "year": 1926,
    "posterUrl": "https://example.org/poster.jpg", "plot": "Optional description",
    "seasons": [{ "number": 1, "title": "Season 1", "episodes": [{
      "id": "aa18a638-a96c-4534-97a8-b60f2fdd56c2",
      "number": 1, "title": "Episode 1",
      "streamUrl": "https://example.org/episode.mp4"
    }] }]
  }]
}
```

Movie items require `id`, `title`, `group`, `streamUrl`; optional `posterUrl`, `year`, `plot`. Song items require `id`, `title`, `group`, `streamUrl`; optional `artist`, `album`, `artworkUrl`, `year`, `durationSeconds`. Series items require show `id`, `title`, `group`, nonempty `seasons`; each season needs a positive `number`, each episode a stable `id`, positive `number`, `title`, `streamUrl`. Episode poster/plot may override the show. Derive category IDs from exact group strings plus type (stable hash), preserve the full label on two lines, and sort by explicit index order within groups unless the user chooses another sort. No `direct_source`, Xtream extension, or Drive file ID appears in a media entry.

Limit each index to **256 KiB / 1,000 items**, a URL to 2 KiB, and text fields to bounded lengths before parsing into Room; cap redirect count and reject `file:`, `content:`, `javascript:`, localhost and private-network hosts in the real Drive adapter. Drive v1 accepts public HTTPS media/artwork links with **no per-link headers, cookies, DRM or expiring signed URLs**. If an imported link needs headers, show “This link needs sign-in headers and is not supported yet”; do not store header secrets in JSON. The mock may use its explicit local HTTP origin. The later OneDrive and WinUI clients must apply the same validation.

On first sign-in, query app-accessible root folders named `Tvivo Library` (`trashed=false`, folder MIME); prefer a previously saved folder ID. With `drive.file`, discovery is limited to files accessible to this OAuth app, so a same-named folder created by another app is **not** silently imported. If none exists, create root, child folders and the three indexes, then write `library.json` last. Seed only this newly created folder: about five movie links, two series with a few episode links, and five song links whose public-domain/sample rights and direct HTTPS playback have been checked at implementation time. Use no embedded media or downloaded poster files; uploaded JSON should be kilobytes. The mock's existing locally generated media can supply deterministic test URLs.

Make bootstrap resumable: persist the new folder ID and `bootstrap=pending` locally before child creation; re-list children by parent/name/MIME before every create; fill **missing** files only while pending; never overwrite an existing index. Write the complete marker only after all three indexes validate. If a complete folder has a missing/empty index, show “Library file missing” with a repair action; do not silently reseed user edits. If two accessible roots have the name, choose the stored ID or ask the user which folder to use. Single-flight local creation prevents duplicate calls; after a timeout, re-list before retrying because Drive may have accepted the create. A storage-quota 403 leaves a visible retryable partial bootstrap and never claims success.

On re-read, request file metadata (`id`, `name`, `mimeType`, `size`, `modifiedTime`, `md5Checksum`, `version`; use HTTP ETag only if actually returned). Compare `id+version` or `md5Checksum` first, with `modifiedTime` as fallback; `modifiedTime` alone is not a safe equality check. Fetch changed bytes with `files.get?alt=media`, validate all three files, then apply each valid changed list in a short Room transaction/generation flip. Distinguish a valid `items: []` (intentional empty) from an absent/corrupt file. Keep the previous local generation on 401, 403, 429, parse failure, timeout or cancellation. This version only reads user edits: no app-side list editor or competing index writes after bootstrap. A future editor must use version/ETag preconditions and resolve conflicts, never last-writer-wins silently. Google Drive v3 `files.list`, `files.create`, `files.get`, metadata fields, and binary download are documented [here](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list), [here](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/create), and [here](https://developers.google.com/workspace/drive/api/guides/manage-downloads).

## 3. Authorization and mock-first rule

- **Phone/tablet:** tap “Sign in with Google Drive”; use Google Identity Services `AuthorizationClient` with only `https://www.googleapis.com/auth/drive.file`, launching its consent resolution when needed. The production adapter gets a fresh access token by calling `authorize()` on later sessions; it does not need to invent a refresh-token flow or store a Play-services-managed token. Keep any token copied into app memory short-lived; if a future implementation persists one, it must use the existing DataStore + Tink AEAD/keyset pattern, excluded from backup. On 401, clear the invalid token and authorize once more; an unresolved denial leaves the previous source active. Drive `about.get?fields=user(permissionId,displayName,emailAddress)` supports `drive.file`; use `permissionId` for stable account partitioning and show email only if returned. No extra identity scope is requested. Google documents [Android authorization](https://developer.android.com/identity/authorization), [the `drive.file` scope](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), and [`about.get` scope support](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get).
- **TV:** use the OAuth **TVs and Limited Input devices** client. `POST https://oauth2.googleapis.com/device/code` with `client_id` and `drive.file`; display the returned `verification_url` and case-sensitive `user_code`, with expiry countdown. Poll `POST https://oauth2.googleapis.com/token` using device-code grant at the server-provided interval; handle `authorization_pending`, `slow_down`, denial, expiry and cancel. Store the returned refresh token encrypted with the same Tink/DataStore pattern under a distinct associated-data version; store access token only in memory where possible. Refresh through the token endpoint before Drive calls, serialize concurrent refreshes, replace a rotated refresh token atomically, and treat `invalid_grant` as reauthorization needed while preserving cached rows. Google's [TV device-flow guide](https://developers.google.com/identity/protocols/oauth2/limited-input-device) is authoritative; confirm its current client-secret requirement for the configured TV client during real-client wiring and never treat a distributed client secret as confidential.
- **Sign out / switch:** switching source never revokes the current grant until the new source is accepted. Offer local “Stop using this source” separately from explicit “Disconnect Google Drive”; the latter uses `AuthorizationClient.revokeAccess` on phone/tablet or the OAuth revoke endpoint on TV, then deletes that source's local encrypted token and active pointer. Warn that Google OAuth revocation can invalidate grants for **all clients in the same Cloud project**, including another Tvivo device. No in-app action deletes Drive indexes in v1. If revocation fails offline, remove the local active token and report that Google access may need removal in Google Account settings. Never clear Tvivo app data or Tink's keyset as a shortcut. The existing Xtream sign-in and sign-out path remains operational.
- **Offline:** a previously synced Drive library opens immediately from Room without an OAuth round trip; show “Showing saved library · last synced …”. First use without connectivity shows “Connect to set up Google Drive” and a retry action, with no fake empty catalog. Token expiry during offline use affects refresh only; external media links themselves still need connectivity.
- **Failure copy:** 401 “Google Drive access expired. Sign in again”; 403 `storageQuotaExceeded` “Drive is full. No library files were changed”; other 403 “Tvivo cannot access this library”; 429 “Drive is busy. We'll retry later”; corrupt/unsupported JSON “This library file needs repair. Saved titles are still available”; slow/offline “Can't refresh now. Showing saved titles.” Map by Drive error `reason`, not HTTP status alone. Google lists these [error reasons and retry guidance](https://developers.google.com/workspace/drive/api/guides/handle-errors).
- **Local mock first:** add a sibling `tools/mock-drive/` server so the existing Xtream mock and its `__ctl` controls stay intact. Expose mock `/device/code`, `/token` (including refresh and revoke), `/drive/v3/about`, `/drive/v3/files` list/create/get metadata, `/drive/v3/files/{id}?alt=media`, and multipart upload; model two accounts, app-created-file visibility under `drive.file`, pagination, version/modifiedTime, create-after-timeout, and bearer-token expiry. Provide deterministic control endpoints for 401, 403 quota/permission, 429, delay, offline/drop, duplicate folder and corrupt JSON. A fake phone authorization adapter returns mock bearer tokens; no Google UI or client ID is needed for local QA. Keep mock tokens and fixture URLs synthetic.

## 5. Playback and cache behavior

- Map each Drive movie/episode/song to a typed `PlayableMedia` holding its **direct validated URL** and source/account/item identity; `StreamUrlBuilder` remains Xtream-only. Resolve from Room at activation so a stale Intent cannot carry an old URL after an index edit. Existing movie/episode pre-run pages, favourites and resume work through the source-neutral item key. Do not open a stream merely by browsing or running an automated test.
- `PlaybackService` remains the **single ExoPlayer and MediaSessionService owner**. Add an audio-only content mode for songs: music audio attributes, metadata (title/artist/artwork), hardware and notification play/pause/previous/next, queue order from the chosen group, noisy-device and audio-focus behavior, background continuation, and checkpoint/resume where duration exists. Reuse `SleepTimerPolicy` and its notification controls. The Music screen and mini player bind to the same session; leaving the screen does not create a second player. Video/Cinema mode, current live/episode queue behavior, and Xtream URL handling are unchanged. A new queue replaces the old session deliberately, with no simultaneous streams.
- Indexes and artwork use separate budgets: no poster download during Drive sync; reuse the current sized image pipeline for cards. First sync validates and commits each list, then opens cached rows. Subsequent entry renders Room immediately and schedules a coalesced refresh; 24 h background WorkManager refresh when allowed, plus explicit “Re-sync now” bypassing TTL. Compare remote fingerprints before downloading bytes. One in-flight sync per account; account/source generation guards reject stale completion. Cap retries with jittered exponential backoff for 429/transient 5xx, honor `Retry-After`, never spin on quota/permission errors, and allow cancellation. Metered/Wi-Fi-only catalog policy follows the existing product commitment; media playback remains a user action. No refresh blocks the UI or clears saved rows on failure.

## 6. Security, privacy, and owner's later Google setup

Only `drive.file` is requested. Drive receives OAuth consent, folder metadata and index reads/writes; media and poster hosts receive the user's normal playback/image requests, so show that fact in privacy copy. No index contents, email, token, URL, device code, or account ID go to diagnostic logs or crash export; log bounded operation names, status/reason and timings only. Never send Drive bearer tokens to a media URL. External links are untrusted input: enforce URL/scheme/host limits, bounded parsing, TLS validation, redirects that stay within policy, and safe error messages. Keep all credential I/O off the main thread, in DataStore + Tink under Android Keystore as in `CredentialsStore`; exclude token store from backup. Keystore invalidation can make all encrypted credentials unreadable; prompt for active-source reauthorization while preserving account-scoped Room catalog, favourites and resume. Google client IDs are configuration, not passwords, but keep owner-specific values and any TV client-secret value out of git per repo policy.

**Owner checklist for real Google wiring after mock QA:**

1. Create/select one Google Cloud project, enable Drive API, configure Google Auth Platform branding, support contact and privacy-policy URL; declare only `drive.file` for this feature. Google classifies it as non-sensitive with basic verification, not the restricted Drive scope process. [Scope guide](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).
2. Keep consent screen in **Testing** for QA and add each intended Google account as a test user. Expect Testing authorizations, including refresh tokens, to expire after seven days; plan reconnection during QA. [Audience guidance](https://support.google.com/cloud/answer/15549945).
3. Create Android OAuth client(s) for the app's actual package name and **debug, release/upload, and Play App Signing SHA-1** fingerprints as applicable; supply client ID(s) through local untracked configuration. [Android client authentication](https://developers.google.com/android/guides/client-auth).
4. Create a **TVs and Limited Input devices** OAuth client in the same Cloud project; provide its client ID and any required distributed-client credential through local untracked configuration, then verify device-code polling with the real endpoint. [TV setup](https://developers.google.com/identity/protocols/oauth2/limited-input-device).
5. Run a one-account, one-folder real-Drive smoke only after the mock suite passes and the owner authorizes it. Verify that Android and TV clients in the project see the same app-created files; later verify the WinUI OAuth client can read them with `drive.file` before promising cross-device access. Publish beyond Testing only after consent/privacy review.

## 8. Risks and truly blocking owner choices

- **Near-full Drive:** even tiny JSON/folders may fail quota. Bootstrap must stop cleanly, keep its pending state, and show the exact quota copy; no hidden large uploads. Exact public-domain/sample URLs and rights need verification before a real seed; mock-generated local media is sufficient for mock QA.
- **`drive.file` visibility across OAuth clients:** the folder is app-created, but Android/TV/WinUI client behavior needs a real project smoke before cross-device support is promised. A pre-existing same-name folder created elsewhere is outside the approved scope. No broader Drive permission is the fallback.
- **Android authorization and TV refresh differ:** Google Play services owns handset token renewal, while TV refresh tokens are app-held. The `SourceAuthorization` interface must model both without persisting unnecessary phone tokens.
- **Existing routes are Xtream-shaped:** numeric item IDs, `Credentials` in routes, and direct URL building are the largest regression risk. The source-session seam and separate Drive tables are prerequisites; forcing Drive links through the old Xtream path is rejected.
- **Owner input that blocks real Google smoke only:** Cloud project/test-user access plus Android and TV OAuth client IDs, package/SHA-1 registrations, and approval for that real-account test. No owner decision blocks mock-first implementation. OneDrive provider choice and an index editor are deferred.
