# Android TV ↔ WinUI parity audit

**Scope:** source and documentation audit of `codex/winui-catalog-design-plan` against the current Android app. No files other than this handoff were written. No build, app launch, stream, or runtime verification was performed. Status describes Android parity with the WinUI user-facing behavior; WinUI-only behavior is used as the comparison baseline.

**Status key:** HAVE = Android has substantially the same user behavior; PARTIAL = a related path exists but differs materially; MISSING = no equivalent found; N-A = Windows-specific behavior does not transfer directly. For every PARTIAL/MISSING row, effort is S/M/L and product-decision need is stated. Paths are repository-relative.

## Shared-logic candidates to reimplement in Kotlin

These are deterministic or persistence-domain policies in `windows-spike/src/Tvivo.Core/` that could be ported if the product choices are accepted. They are not shared binaries or UI abstractions; Android remains native Kotlin/Media3/Room.

| C# core candidate | Android-side use | Notes |
|---|---|---|
| `EpisodeCompletion.cs` (`EpisodeCompletion`, `MovieCompletion`) | `PlaybackStateRepository.savePosition` | Port only after deciding whether to replace Android’s shared 92% completion threshold with per-kind fixed tails. |
| `PlaybackMode.cs`, `NextPlaybackSelector.cs` | `PlayerActivity` and playlist selection | Kotlin policy + seeded/random selector; persist episode/movie modes independently. Current WinUI defaults Next for episodes, Shuffle for movies. |
| `NextPrompt.cs` | Android player overlay/timer | Pure timing policy; requires the playlist-mode behavior and prompt UX decision. |
| `HeldSeekAccelerator.cs` | D-pad key hold handling in `PlayerActivity` | Can translate elapsed hold duration into increasing seek steps; preserve a short-press contract and cancellation behavior. |
| `TrackSelection.cs` | Media3 track selection/preferences | Port language normalization, subtitle off/default policy, labels, and secondary-track preference; engine mapping must use Media3 APIs. |
| `PlaybackProgressPresentation` in `SqliteCatalogRepository.cs` | Grid/episode row presentation | Convert stored resume/duration/finished values into hidden/partial/full progress semantics for Android cards and episode rows. |
| `PlayerPresentationPolicy.cs` | No direct window-mini equivalent | Only the platform-neutral eligibility and overlay visibility concepts may transfer; Windows HWND/window geometry/minimize policy is N-A. |
| `Epg.cs` | Android Live guide domain types | Porting shapes alone is low value until a supported provider EPG endpoint and guide UX are chosen. |

## Reverse parity: useful Android behaviors WinUI lacks or implements differently

- **D-pad-specific focus contracts:** rail-to-grid focus entry, stable item-ID restore after details, pending episode restore, and focus frame are explicit in `app/src/main/java/com/dev/Tvivo/ui/browse/ContentGrid.kt`, `BrowseScreen.kt`, and `ui/series/SeriesDetailScreen.kt`. WinUI is mouse/keyboard desktop UI and has a different focus model.
- **Pre-run detail page before any stream opens:** Android OK activation opens `ui/detail/ItemDetailScreen.kt`; long-press context menu is the direct-play shortcut (`ui/browse/ItemContextMenu.kt`). This is a deliberate TV safety/decision step; WinUI starts from its desktop browse/player surfaces.
- **Room-backed incremental per-category TTL cache plus asynchronous full-catalog sync:** `data/repository/CachedFetch.kt`, `sync/CatalogSyncer.kt`, `sync/RefreshWorker.kt`, and Room DAOs. WinUI uses account-scoped SQLite snapshots and has no Android WorkManager lifecycle.
- **TV-first category rail and channel/poster card geometry:** `ui/browse/CategoryRail.kt`, `ContentGrid.kt`, `VirtualFolder.kt`. WinUI uses top navigation/search and desktop shelves.
- **Remote-friendly login and account safety:** encrypted credentials (DataStore + Tink), D-pad fields, guarded sign-out, and non-destructive change-account path (`auth/`, `ui/common/DpadField.kt`, `ui/settings/SettingsScreen.kt`). WinUI has a desktop setup page and credential store, but not Android TV IME/focus constraints.
- **Explicit app-wide diagnostics UI with export, clear, runtime/DB metrics and local catalog profiling:** `ui/settings/DiagnosticsScreen.kt` and `diagnostics/`. WinUI currently records richer structured playback lifecycle logs, but the settings diagnostics screen was removed.
- **Series parser and cache protections:** Android `data/remote/SeriesInfoParser.kt` handles string episode IDs, trustworthy duration-field fallback, and resilient empty/error refresh behavior in `SeriesRepository.kt`; preserve these panel-specific behaviors in any port.

## Top 10 Android TV follow-ups (remote usability first)

Ranks combine how often the remote user encounters the gap, the impact of the behavior, and dependency order. An item with a product decision should be agreed before implementation; this audit itself did not decide the UX.

1. **Episode row progress/watched cue (PARTIAL, M):** show unstarted, partial, and watched state in the season episode list; make it legible at TV distance and retain episode-ID focus restore. Depends on completion semantics.
2. **Watched state and completion rule (PARTIAL, M):** choose fixed-tail vs current 92%, store a watched state rather than only deleting resume, and offer a clear user-visible label/action if desired.
3. **Play-next modes per content kind (MISSING, M):** decide defaults (WinUI currently Next episodes / Shuffle movies) and remote-operable Off / Next / Shuffle controls. Prevent unwanted auto-play.
4. **Next-item prompt timing and cancel path (MISSING, M):** after mode agreement, add accessible D-pad controls, seek-out/re-entry behavior, and prompt lead timing.
5. **Audio/subtitle selector (MISSING, M):** useful for the documented language-selection issue; expose stable D-pad track names, subtitle Off, selected state, and language preference.
6. **Interactive seek bar (PARTIAL, S):** retain current ±10s D-pad seek while making the time bar a focusable/scrubbable control with predictable left/right increments.
7. **Accelerated held seek (PARTIAL, S):** speed up long key holds while preserving a reliable short press and stopping cleanly on key-up/focus loss.
8. **Recently played shelf/folder (MISSING, M):** decide whether a TV user benefits from a short recently-played list, distinct from Continue Watching and Favorites.
9. **Catalog browse sort control (MISSING, M):** add only a small set of D-pad-friendly choices (for example title / newest / recently played) after choosing semantics; avoid desktop-style dense sort controls.
10. **EPG Now/Next (MISSING, L):** first confirm a usable endpoint beyond the current provider’s unavailable XMLTV path, then add a focusable Now/Next affordance for Live rows/player.

Possible follow-ons after these: decide whether NEW-since-visit badges belong in the TV rail, whether the My Tvivo landing should use horizontal rows, user-facing suggestions, and whether Player preferences deserve a separate account/settings destination. Quality badges are low effort but lower impact than the above remote workflows.

## Six-part report

### VERDICT

Android TV already covers the catalog core: content-type/category browsing, search, favorites, Recently Added, Continue Watching, series/episode selection, resume prompts, catalog refresh, change-user/sign-out, and remote seek controls. Parity is materially incomplete in playback progression/state: no watched marker, episode progress cues, play-next modes, next-item prompt, interactive seek bar, or audio/subtitle chooser. WinUI’s sort/history/NEW badges and desktop playback/window affordances also do not map fully to Android TV.

### STRONGEST EVIDENCE

The clearest source comparison is `windows-spike/src/Tvivo.Core/{PlaybackMode,NextPlaybackSelector,NextPrompt,EpisodeCompletion,HeldSeekAccelerator,TrackSelection}.cs` and `windows-spike/src/Tvivo.Infrastructure/SqliteCatalogRepository.cs` against Android `app/src/main/java/com/dev/Tvivo/ui/player/PlayerActivity.kt`, `ui/series/SeriesDetailScreen.kt`, `data/repository/PlaybackStateRepository.kt`, and `data/remote/SeriesInfoParser.kt`. The most recent branch commits (`1a992ab`, `0634186`, `3615ae6`, `a3158e8`, `a3fe53f`) specifically add mini mode, play-next/hold seeking/completion, progress and cinema controls, track selection, and EPG. Android source directly confirms its 92% completion cutoff, non-interactive ProgressBar, fixed ±10-second seek, no playlist controls, and duration parser fallback.

### EXACT BOUNDARY

Read-only source/docs audit. No tracked files changed; only `.tmp-codex-parity-handoff.md` was created. No builds, tests, app launches, provider requests, streams, UI automation, or runtime observations were made. Effort sizes and ranking are planning estimates, not implementation commitments.

### RULED OUT

This report does not recommend porting Windows window geometry, minimize-to-mini, MSI, or pointer hiding into Android. It does not propose replacing Android’s native Kotlin/Media3/Room stack. It does not treat WinUI-only metadata tooltip behavior as a TV requirement: Android already has a pre-run detail page. It also does not claim that XMLTV/EPG will work against Android’s configured provider.

### UNCERTAINTY

The audit is limited to checked source and current documentation, not live UI behavior. Android has pending D-pad/emulator verification items in `TODO.md`; WinUI documentation itself notes open verification for the newly added EPG and track picker, next-item prompt, and window-mini flows. Provider EPG support beyond the observed XMLTV 404 is unknown. Android’s repeated key-down behavior for a long hold was not run; code shows fixed increments and no accelerator policy. WinUI no longer has a Diagnostics settings screen, while its structured logs are not a user-facing diagnostics page.

### NEXT GATE

Make product calls on completion/watched semantics, autoplay modes/defaults and prompt behavior, track-language defaults, and whether Recently Played / sort belong on the Android TV surface. Then implement one coherent D-pad batch beginning with episode progress and playback controls, validate with safe local fixtures/unit tests, and request the separately required approval before any emulator deployment or live stream validation.
