# Android file size parity and phone downloads — implementation plan

**Status:** plan only, 2026-11-04. Branch `android/finalize-parity`. No implementation or device result is claimed. The working tree already contains unrelated edits; each job must preserve them. Android is one codebase for TV, phone and tablet; **size is for TV and phone**, while **downloads are phone only** in this plan. Tablet download scope is an owner decision.

> **Implementation status 2026-11-05 (JVM-verified, no device acceptance):** jobs 1-4 (size table, parsers, probe, labels), 5 (media-connection coordinator, `docs/media-connection-coordination.md`), 6 (downloads table v10, cap, quota), 7 (queue UI, cap warning, Settings), 8 (resumable worker, notification), 9 (race fix, Downloads screen, offline playback) and 10 (ledger) are committed on `android/finalize-parity`. Not done: automatic exact-size probe when an item opens, size labels on browse cards, device passes (phone download, offline PiP/notification, TV/phone playback with the coordinator), WinUI downloads. Provider probe findings: newest stream cuts the older one silently; `active_cons` unreliable; connects drop intermittently; HEAD/Range on live gives no length.

## Baseline and product boundary

- WinUI `codex/winui-catalog-design-plan` commits `c1cad81`, `bb0be31`, `a828237` show `File size: 1.4 GB` on movie hover/Spotlight cards, episode rows and player details; exact size wins over `~1.4 GB` estimates. A series has no single file size. `FileSizeAvailabilityPolicy` bounds absent-size metadata rechecks to seven days; **opening** a movie/episode with no exact size bypasses that wait. `HttpFileSizeProbe` tries HEAD `Content-Length`, then GET `Range: bytes=0-0` and accepts only a valid `206 Content-Range` total (or valid HEAD `200` length), 1 MB–200 GB, with a combined roughly two-second timeout and no response-body read. It runs after the old player stops and before the next media open. `SaveMetadata` stamps `size_checked_at` only when an actual size arrives; a probe may record an absent attempt, but that stamp never suppresses an open-item probe. Count-only coverage and found/none/failed/skipped reason diagnostics reveal missing provider fields without logging URLs.
- The redacted `windows-spike/docs/provider-field-report.md` (read with `git show codex/winui-catalog-design-plan:windows-spike/docs/provider-field-report.md`; absent on this branch) reports 0 of 49,043 movie-list rows with a size-like field; sampled VOD/episode info had bitrate and duration but no size. Android `VodInfoParser.Details` and `EpisodeEntity` currently omit bitrate and size. The Android schema is **v8 at HEAD** (`AppDatabase.kt`), despite older bible text saying v7/v5. `CatalogSyncer.syncVod`, `VodDao.replaceCategory`, and `SeriesDao.replaceEpisodes` replace rows, so size knowledge needs storage independent of those rows.
- Product assumption: **file size and phone downloads are free**. `PRODUCT-BIBLE.md`/`docs/android-production-plan.md` list Plus v1 features and do not list downloads; offline access plausibly meets the free-core rule. Do not add a Plus gate without an owner decision. No ads, provider branding, hosted content, or in-app Plus purchase route outside Play Billing. Downloads apply only to media the user has a legal right and provider permission to save; the player must not claim rights or bypass DRM. A server may reject HEAD/Range, prohibit saving, serve expiring URLs, or return protected media; disable download for those items and explain why. Confirm Play policy and provider terms before release; this repository cannot establish rights for arbitrary sources.

## A. Size parity: shared data, TV and phone presentation

1. **Room v8→v9:** Add an account-scoped `media_file_sizes` table (`MediaFileSizeEntity` in `data/local/entities/`, `MediaFileSizeDao` in `data/local/dao/`, `AppDatabase.MIGRATION_8_9`). Key movie by `(accountId, movie, streamId)` and episode by `(accountId, episode, seriesId, episodeId)`; episode ID stays a string. Store nullable `exactBytes`, `estimatedBytes`, `lastProbeAt`, `lastProbeOutcome`. Do not create series or live size records. Keep `metadataFetchedAt` separate from probe time. A missing metadata field must not change `lastProbeAt`; a failed/absent probe may record its attempt without deleting a prior exact value. This independent table survives full generation flips and category/episode replacement. Real migration only; preserve favourites, resume and every v8 user table. Export schema 9 and test old→new chains.
2. **Metadata and estimate:** Extend `data/remote/VodInfoParser.parseDetails` and `SeriesInfoParser.parse` to accept tolerant `size/filesize/file_size/size_bytes` fields (number or decimal-unit string) and bitrate; keep `duration` ahead of `duration_secs`. `VodRepository.fetchDetails` and `SeriesRepository.refreshSeriesInfo` write known sizes/estimates through the size DAO, never stamp a missing field as a successful size check. Pure `FileSizeEstimatePolicy`: total bitrate 128–80,000 kbit/s × duration 60–28,800 s ÷ 8, result 1 MB–200 GB; no estimate when inputs are implausible. Store estimate separately and render `~` only when exact is absent. Catalog refresh may record count-only `itemsParsed/itemsWithSize`, but must not launch thousands of probes.
3. **Exact probe and connection order:** New `data/remote/HttpFileSizeProbe` uses OkHttp headers-only, one global probe at a time, two-second total deadline, strict HEAD/Range parsing and cancellation. Use `StreamUrlBuilder` for movie/episode URLs; never persist or log a credential-bearing URL. One app-wide `MediaConnectionCoordinator` (with account identity on each lease) must serialize probe, download, and `PlaybackService` HTTP opens; the existing `SingleStreamDataSourceFactory` gate covers player data sources only. At `MainActivity.playItem` and the episode play route, stop/release the prior media connection, attempt one probe if exact is missing, then start `PlayerActivity` regardless of timeout/failure. A newly opened item bypasses the seven-day absent recheck interval; background metadata rechecks remain bounded to once per seven days and cannot open a media socket while playback/download uses it. Session/generation IDs discard stale results. No probe for series, live, offline local files, or repeated player recovery/next-frame requests. A download action may reuse a fresh exact size or run this same probe only after acquiring the lease.
4. **UI:** Add preferred exact/approximate formatting and accessible wording in a shared `FileSizeFormatter`. TV: `ui/browse/ContentGrid.StreamCard`/`SearchContentCard`, `ui/components/ShelfCard`, `ui/detail/DetailHero` and `ui/series/SeriesDetailScreen.EpisodeRow`; phone: the same card/detail components under the adaptive shell. Render `File size: 1.4 GB` or `File size: ~1.4 GB` with semantics saying “Approximate file size”; hide when unknown. Movie cards use batched observable size lookups for visible IDs through `BrowseViewModel`/shelf view models, avoiding one DAO query per card; episode rows observe their IDs. Series cards/details and live cards never show a size. Keep title/quality, 220×330 and 220×124 decode targets, TV focus, and Arabic RTL intact.
5. **Evidence:** JVM tests for parser aliases and missing fields, estimates and format, strict `Content-Range`/chunked/oversize/timeout with MockWebServer, skip/failure diagnostics (reason categories only), Room v8→v9 plus old-chain preservation and refresh replacement, and TV/phone Compose label/semantics tests. No automated test opens a real stream. Device acceptance (owner-approved later): TV D-pad card/detail/episode focus and movie play handoff; phone labels in portrait and RTL; mock-provider HEAD success/fallback/failure. Re-run [protected P1–P6](protected-features.md) JVM gates, then owner-approved TV device smoke before calling parity HAS.

## B. Phone downloads

**Engine recommendation:** an app-owned, foreground `CoroutineWorker` using OkHttp and a persisted Room queue. It writes one progressive `.mp4`, `.mkv`, or `.ts` file per movie/episode; it does not save HLS or live TV. This gives the cap, range-resume, byte accounting and connection preemption one owner. Media3 `DownloadManager`/`DownloadService` is a good cache-based offline engine but stores cache spans rather than a simple file and would still need custom quota/lease integration. Android's system `DownloadManager` owns scheduling and partials, making the strict pre-start reservation, mid-transfer cap, and playback preemption harder. WorkManager supports foreground long-running workers, but Android 16 job quota can affect them; review a user-initiated data-transfer job or direct foreground service at target-SDK update before release ([Android WorkManager guidance](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running), [Media3 download model](https://developer.android.com/media/media3/exoplayer/downloading-media)).

- **Storage/state:** `getExternalFilesDir(Environment.DIRECTORY_MOVIES)/downloads/` with opaque account-scoped filenames, `.part` until verified and atomically renamed to the source extension. App-private, no public Downloads scan or storage permission; use internal app storage only if a deliberately chosen destination has enough space. `DownloadEntity`/`DownloadDao` in Room v9→v10 stores account, movie/episode identity, series ID, extension, state, expected bytes, actual partial bytes, ETag/Last-Modified (if supplied), and safe local relative path. Never store credential URLs. Reconcile DB with actual file lengths at startup and before quota checks. Keep completed files available offline when the source is unreachable; exclude them from catalog-refresh deletion. Account switch hides other accounts' downloads; sign-out handling needs the owner's retention decision before implementation.
- **Settings/cap:** Phone Settings → Library → Downloads: “Download limit”, “Used”, “Available”, “Manage downloads”. Proposed default **20 GB**, selectable **1–500 GB** in whole decimal GB (`1 GB = 1,000,000,000 bytes`), device-wide across accounts, persisted in a separate DataStore `DownloadPreferencesStore`; TV has no control. “Used” is sum of actual completed file lengths plus actual `.part` lengths, including paused/failed partials. Show queued **reservations** separately; reservations are not billed as used bytes but prevent simultaneous queue oversubscription. Lowering the cap below used pauses all downloads and blocks new starts; existing files remain.
- **Pre-start flow:** Phone movie detail gets Download; episode row gets Download and season selection offers “Download selected episodes” (series show itself is never downloadable). Before any **transfer** socket opens, resolve each item to exact size (cached or serialized HEAD/Range probe) and display “Used X + queued Y + this item/batch Z = projected total; limit L”, naming exact vs `~` estimate. For estimates reserve a conservative 1.5× estimated bytes and say the result may be larger. If projected total exceeds the cap, show a warning **before enqueue/start** with Cancel and Manage downloads/Increase limit; do not start until it fits. For a queue or season batch, sum all chosen episodes plus existing reservations atomically in one Room transaction; show count and total, and let the user remove selections. Unknown size after probe: default **block downloading** with “Size unavailable; download cannot be checked against your limit” and offer Stream instead. This is the only way to guarantee the stated pre-start limit. A changed server total or duplicate queue entry triggers a fresh transaction/check before transfer.
- **Transfer:** One worker and one media socket **per app**, regardless of reported `UserInfo.maxConnections`; no parallel batch transfers or cross-account overlap. This conservative rule also protects accounts used on another device, which `active_cons` cannot reliably reserve. Playback has priority: when Play is pressed, show “Download paused while you watch”; request worker pause, close its HTTP response/socket and await acknowledgement, then permit the size probe and player open. If close cannot be confirmed promptly, do not open a competing stream; show Retry/Cancel download. Paused playback still owns the stream slot until service release. Once playback fully stops, the user may resume the queued download; no silent auto-resume. On an account reporting `max_connections=1`, explain that a download uses the same provider connection as playback; report the provider's value, never a product-wide limit. If the provider rejects downloading or other devices consume the slot, pause with a recoverable message rather than retrying aggressively.
- **Resume/retry/control:** Resume with `Range: bytes=<actual .part length>-` and `If-Range` validator when available; accept only a matching `206` total/start. If range is ignored, validator changes, or content is compressed/chunked, discard the stale partial **only after explaining** that restart is required and rechecking quota/space; do not append corrupt bytes. Bounded exponential retry for transient network/5xx, stop on auth/rights/DRM/unsupported responses. Pause preserves partial and reservation; Cancel asks whether to delete partial (default delete), releases reservation and worker. Foreground notification has progress, Pause/Resume, Cancel; Android 13 notification denial must not make transfer silent or break its required foreground service. Default Wi-Fi-only; a metered override needs an explicit per-batch confirmation. Pause on low battery (proposed under 15% and unplugged), resume when charged at user request. Before start and each write/checkpoint, enforce both cap and free-space reserve (proposed 500 MB); on either limit pause, close socket, keep the partial, and offer Delete or Increase limit/free space. Never let the file exceed the configured cap; a server size increase requires a new warning and approval before continuing.
- **Offline playback/deletion:** Phone Downloads list opens only completed local media through `PlayerActivity` → existing `PlaybackService`/Media3 player, using an app-private `content://` URI or validated local URI and the existing movie/episode ID, resume and favourites. `SingleStreamDataSourceFactory` must bypass the HTTP lease for local files; no network probe on offline play. Playing a deleted/missing file shows a recovery action, never silently streams online. Episode auto-next uses a local file only when complete; otherwise asks before network playback. Deletion stops playback of that file first, removes `.part`/complete file and Room row, updates usage and reservations atomically enough to reconcile after crashes; never touches favourites or resume. No provider URL, credential, or raw title in diagnostic export.

## E. Risks and owner decisions

| Question (recommended default) | Why it matters |
| --- | --- |
| Is phone download free? **Yes.** | Neither bible lists it as Plus; adding a gate changes the free/Plus promise. |
| Is tablet included? **DECIDED by owner 2026-11-04: yes, phone AND tablet; TV excluded (small memory).** | Same download code on phone and tablet; the adaptive shell must show the Downloads entry on tablet layouts too; TV hides it. |
| May an unknown-size item download? **No; stream instead.** | A pre-start cap warning cannot be truthful without a bound. |
| Should download and playback ever overlap when `max_connections ≥ 2`? **No, serialize in-app.** | Other devices may occupy slots; reported maximum is not a reservation. |
| What happens to files on account sign-out? **Ask clearly, then delete that account's files; switch-account retains them hidden.** | Avoid surprising loss and cross-account access. |
| Does WinUI need downloads? **DECIDED by owner 2026-11-04: yes, WinUI gets downloads next.** Ledger: `A-PHONE-DOWNLOAD*` WinUI = MISSING (planned), plan a separate desktop job after the Android design settles; the cap/warning semantics here are the shared spec. | Keeps both apps aligned; the connection-counting finding (see `tools/provider-probe/`) affects both. |

Major remaining risks: provider HEAD/Range behavior and terms vary; bitrate estimates can be far off; foreground transfer policy and Android 16 quotas need current-target verification; storage can disappear/fill during a write; probe/download/player lifecycle races are more serious on one-connection accounts. Validate these with the local mock provider and owner-approved devices, never a real-provider automated stream.
