# Media connection coordination

`MediaConnectionCoordinator.shared` is the process-wide owner of provider media access. PlaybackService reserves a PLAYBACK session before preparing an HTTP item and releases it after its Media3 source closes. A loaded item remains active while buffering, playing, or paused. Local files bypass the HTTP bridge. Media3 loader threads use the blocking bridge; future workers call `withSlot(DOWNLOAD, ...)`, and explicit size lookups call `MediaFileSizeRepository.probeWhenIdle(...)`. No screen starts a probe automatically yet.

Completed offline downloads use the existing player without calling `beginPlaybackSession`: a local URI cannot consume a provider connection, so it must not preempt or pause a download. HTTP playback keeps the existing PLAYBACK-session preemption behavior.

The state machine is **idle → playback / download / probe → idle**. There is one background lease at a time. A PLAYBACK session immediately cancels a DOWNLOAD or PROBE lease with typed `Preempted`; its loader waits at most two seconds for cooperative socket closure, then fails the open safely. The worker must close the socket in `finally`, persist its actual `.part` length in a non-cancellable cleanup, and reschedule with Range after `Preempted`. A user cancellation remains ordinary `CancellationException`. Downloads and probes never preempt. Waiting downloads run FIFO before waiting probes; probes run only with no playback or download active. `state: StateFlow<Snapshot>` exposes owner, session-active flag, and queue counts without provider polling. Labels are safe descriptions, never URLs or credentials.

After **any** completed media holder closes, a background opener waits a configurable six-second quiet gap. The measured provider slot freed in about five seconds, so six seconds gives a small margin without delaying playback. Background connect failures (`ConnectException` or `SocketTimeoutException`) release the lease and retry up to four attempts with exponential 1/2/4-second delays plus 0–25% jitter, subject again to the quiet gap. Playback keeps its existing `SingleStreamConnectionGate` release-before-open and recent-close 403 handling; it gains no retry or quiet gap. A failed/open-ended background holder cannot be forcibly disconnected by this class: it must honor coroutine cancellation and close its socket; playback's two-second acknowledgement timeout prevents an unsafe second open.

The owner's provider accepted a second stream with HTTP 200 but silently cut the older one. Live A stopped flowing when live B opened. `active_cons` was zero while a stream was open, so it is never a scheduling input. VOD HEAD returned Content-Length, and Range 0-0 returned 206 plus Content-Range; live HEAD/Range supplied no length. A second full read of the same VOD was accepted. The slot became free about five seconds after close. New TCP connects intermittently timed out or returned ETIMEDOUT. Cut live streams cannot resume; VOD can resume with Range. It remains **unknown** whether HEAD, Range, or re-open during live playback cuts live playback; the coordinator assumes they do.

**V2 idea, untested and not built:** interleave VOD playback and download in short Range chunks after measuring whether the provider preserves playback. Do not apply this to live streams or infer safety from HTTP 200.
